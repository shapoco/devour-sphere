# Devour Sphere (Xiamocon 版)

[Xiamocon](https://github.com/shapoco/xiamocon) (XIAO RP2350 用のゲーム機型マザーボード)
で core/ を動かすためのファームウェア。
ゲームのルールと描画はすべて core/ 側にあり、ここには
「実機へのビルド」「表示への転送」「入力」だけがある。

Xiamocon SDK のグラフィックス API (`xmc::gfx2d` / `gfx3d` / `FrameBuffer`) は使わない。
描画は core/render の `Renderer::renderBand()` + ShapoGFX で行い、
SDK からは表示転送・DMA・入力・電源管理といった足回りだけを借りる。

## 必須要件

- 画面は 240x240 (ST7789)。HUD のレイアウトは core/ 側が解像度から動的に決めるので
  (core/SPEC.md の HUD 参照)、正方形でも破綻しない。
- フレームバッファを 1 枚も持たず、40 行の帯を 2 枚交互に使って描画・転送する。
- シミュレーションは 60Hz 固定、描画は追いつける範囲で行う (可変フレームレート)。
- 音は無し。ハイスコアのフラッシュ保存も無し (電源を切るまでは保持する)。
- ターゲットは XIAO RP2350 と XIAO ESP32S3 の両方。ソースは共通で、違いは下記の数点のみ。

## ファイル構成

```
impl/xiamocon/
  SPEC.md              この文書
  devoursphere/        ファームウェアのプロジェクト (ディレクトリ名 = 生成物の名前)
    CMakeLists.txt     RP2350 用 (pico-sdk。リポジトリのホストビルドとは別のトップレベル)
    platformio.ini     ESP32S3 用 (PlatformIO + Arduino)
    include/
      ds_config.hpp    帯の高さ、アリーナサイズ、tick 周期などの定数
      ds_platform.hpp  2 つのターゲットで異なる部分の宣言
      band_writer.hpp
      profiler.hpp
    src/
      app.cpp          xmcApp* エントリ、静的領域、フレームループ、入力変換
      band_writer.cpp  帯の ping-pong と DMA 転送
      ds_platform.cpp  乱数シードとスタック計測 (ターゲットごとの実装)
      profiler.cpp     計測とオーバーレイ (PicoSystem 版 impl/picosystem/ と共有。
                       そのため ds_config.hpp / ds_platform.hpp を <...> でインクルードする)
```

ディレクトリ名が `devoursphere` でなければならないのは、`xmc run` が
`.cmake/<カレントディレクトリ名>.uf2` を探して書き込むため。

## ビルドと書き込み

```sh
source ~/repo/2026/xiamocon/setup.shrc   # XMC_REPO_PATH をリポジトリ側に向ける
cd impl/xiamocon/devoursphere

# XIAO RP2350
xmc build -p rp2350_pico_sdk             # .cmake/devoursphere.uf2 を生成
xmc run   -p rp2350_pico_sdk -d E        # ビルドして書き込み (WSL2、E: はドライブレター)

# XIAO ESP32S3
xmc build -p esp32s3_pio_arduino         # .pio/build/esp32s3_arduino/firmware.bin
xmc run   -p esp32s3_pio_arduino -s /dev/ttyACM0
```

`-p` を省くと両方ビルドする (どちらも通る)。
- 書き込みは Xiamocon をマスストレージモードにしてから行う
  (Down ボタンを押しながら電源ボタンを 3 秒長押し、その後 Down を離す)。
- 反復ビルドは `.cmake/` で `make -j` を直接叩く方が速い。
  `xmc clean` は `.cmake/` ごと消すので、fetch してビルドした picotool も捨ててしまう。
- **PlatformIO は `lib_deps` のローカルディレクトリを `.pio/libdeps/` に*コピー*する。**
  ShapoGFX (submodule) や core/ を更新しても、コピーは黙って古いまま使われ、
  ビルドは成功するのに中身が前のままになる。submodule を動かしたら
  `rm -rf .pio/libdeps` してからビルドすること。
  実際に入ったかは `grep <新しいシンボル> .pio/libdeps/esp32s3_arduino/ShapoGFX/src/...`
  で確かめられる。RP2350 側 (CMake) は `add_subdirectory` なのでこの問題はない。
- SDK は `~/.xmc/` にインストールされたコピーと、開発用のリポジトリ
  (`~/repo/2026/xiamocon/`) の 2 つがある。`~/.xmc/setup.shrc` は前者を指すので、
  リポジトリ側で開発するときは `~/repo/2026/xiamocon/setup.shrc` を読むこと。

## メモリ配分

RP2350A のリンカ領域は `RAM` 512KB (`.data` + `.bss` + ヒープ) と、
`SCRATCH_X` / `SCRATCH_Y` が各 4KB。
**スタックは SCRATCH 領域にあり 512KB とは別枠**だが、
4096 が上限でそれを超えるとリンクエラーになる。
既定の 2KB は `buildSphere()` の 7 段再帰にはやや心もとないので
`PICO_STACK_SIZE` / `PICO_CORE1_STACK_SIZE` を 4096 に上げている。
これは `add_compile_definitions()` でディレクトリスコープに指定する必要がある
(`crt0.S` と `multicore.c` は INTERFACE ライブラリ経由で `xmc_pfm` 側に
コンパイルされるため、`target_compile_definitions()` では効かない)。

`.bss` の実測 (sim の配列上限を絞った後。合計は `arm-none-eabi-size`、内訳は sizeof):

| 用途 | サイズ |
|---|---|
| 3D アリーナ | 65,536 |
| `sim::Game` | 95,360 (上限を絞る前は 136,512) |
| 帯バッファ x2 (240x40) | 38,400 |
| `render::Renderer` | 23,848 (ワイヤーフレームの 2D 線分 11KB を含む。以前は 11,680) |
| SDK / pico-sdk / newlib / TinyUSB ほか | 約 11,800 |
| **合計** | **234,916 (229.4KB / 512KB)** |

`.text` (+ `.rodata` + `.data`) は 299,280 バイト (4MB のフラッシュに対して十分小さい)。
`.bss` は ShapoGFX の更新ではほとんど変わらない (アリーナは固定長の配列で、
その中の割り付けが変わるだけ。ba15719 でレイヤテーブル 24B が増えた)。
フラッシュの方は 8eff034 で +2.7KB、b03055e で +4.3KB、ba15719 で +5.2KB。
`gfx3d.cpp` 単体では 28,256 → 36,368 → 31,812 → 36,916 バイト
(いずれも `SHAPOGFX3D_TEXTURE=0`、Cortex-M33 / -O3)。
増えているのは b03055e の `PackedVertex` デコード経路と、
ba15719 でレコードのレイアウトごとに特化したスパンビルダのぶん。
このゲームは `PackedVertex` を使わないが、これを落とすマクロは無い。
動的確保はしない。`sim::Game` だけで 133KB あるのでスタックには絶対に置かない。

`pico_set_binary_type(copy_to_ram)` は**まだ使えない**。
RAM に載せる必要があるのは `.text` + `.rodata` + `.data` の 299,280 と
`.bss` 234,916 で、合計 **534,196 バイト**。512KB (524,288) を 9,908 超えている
(sim の配列上限を絞った時点では 8.5KB の余裕があったが、ワイヤーフレームの 2D 線分
11KB で `Renderer` が増えた。ワイヤーフレームが三角形バッファから消えたぶん
アリーナを 64KB から 48KB に落とせば収まるはずで、実機の `ARN` を見て決める)。
SPEC の「これ以上速くするには」に書いたとおり、gfx3d のスパンループは
XIP フラッシュ実行の最悪ケースなので、ここを詰められると効く。

### アリーナの大きさ

**ba15719 以降、三角形バッファは「枠の本数」ではなく「バイト予算」**。
ShapoGFX はプリミティブごとに必要なぶんだけのレコードを確保する。
このゲームの実測値 (32 ビット、`SHAPOGFX3D_TEXTURE=0`、4 バイトのエントリ込み):

| レコード | バイト |
|---|---|
| フラット + 深度 | 64 |
| スムーズ + 深度 | 96 |
| フラット + `NO_DEPTH` | 52 |
| スムーズ + `NO_DEPTH` | 84 |

エンティティ・破片・弾・マーカー・星はすべてフラット
(`putKite()` / `putQuad()` は 4 頂点に同じ色を入れ、マテリアルも `VERTEX_COLOR` 無し)。
スムーズになるのはワイヤーフレーム (距離でフェードする)、オーラ、体力警告。

240x240、レベル 1〜7 × 3 シード × 600 tick を AI プレイヤーに回した実測
(12,600 フレーム):

| | 三角形 | ピーク使用 | 三角形バッファ |
|---|---|---|---|
| 現在 (4 レイヤ、アリーナ 64KB) | 255 | **17,359B** | 54,464B |

シーンが本来の大きさ (261 三角形) に達するのに要る三角形バッファは
実機換算で **36,910B**。それを下回ると `buildScene()` の予算が減り、
まずエンティティがフラグメント単位の細かい形を失う
(取りこぼしが始まるのはさらにずっと下)。変曲点以上なら絵は完全に同一で、
これはホストで 12,600 フレームのハッシュが 62KB 以上で一致することを確認している。

現状は**変曲点の 1.48 倍、ピークの 3.07 倍**。

ここに至る経緯:

| 変更 | ピーク使用 (実機バイト) |
|---|---|
| ShapoGFX b03055e (`SHAPOGFX3D_TEXTURE=0`) | 25,056B |
| ShapoGFX ba15719 (レコード可変長化) | 19,136B (−24%) |
| + レイヤ分け (下記) | 17,732B (−29%) |
| + ワイヤーフレームの描き方を変更 (core/SPEC.md) | **17,359B (−31%)** |

LOD は `triBytesTotal - triBytes` から毎フレーム予算を引き直すので、
この余裕は自動的に使われる。

この 3 段階と後述の `SPAN_CAPACITY` の調整で、**アリーナは RP2350 128KB /
ESP32S3 96KB から両方 64KB になった** (`.bss` が 64KB、ESP32S3 の DRAM が 32KB
空いた)。余裕は以前と同等のまま、必要なメモリが半分以下になっている。

### スパンプールの容量

`Config::spanCapacity` (ShapoGFX ba15719 で設定可能になった) を **128** にしている。
既定はアリーナの残りの 1/4 — 96KB のとき 451 スパン、23KB — を取るが、
実測ピークは 240x240 で 32 しかない。

| 解像度 | `spanPeak` |
|---|---|
| 240x240 | 32 |
| 320x240 | 35 |
| 480x320 | 54 |
| 640x480 | 56 |
| 1280x720 | 59 |

**解像度を上げてもほとんど増えない**。1 本のスキャンラインを横切るプリミティブの
数で決まるもので、スキャンラインの長さではないため。128 は 240x240 での 4 倍、
どの解像度で見ても 2 倍以上の余裕がある。

溢れるとスパンが落ちて絵に穴が空くので、これ以上削るべきではない。
プロファイル表示の `SPN` 行が実測ピークと取りこぼし数を出す。

WASM 版は既定のまま (メモリに余裕があり、大きな画面も描くため)。

### レイヤ分け

`beginLayer()` はシーンを「それぞれ独立に Z ソートされ、後に開いたものが手前に来る」
区間に分ける。`LayerFlags::NO_DEPTH` を付けると深度平面 (12B) もソートも省かれる。
`buildScene()` は 2 つ開いている (星とワイヤーフレームは 3D パイプラインを通らなくなった。
core/SPEC.md「星とワイヤーフレームは 2D で描く」。以下はそれ以前の 4 レイヤ時代の記録):

| レイヤ | 内容 | フラグ | 根拠 |
|---|---|---|---|
| 1 | 星 (現在は 2D) | `NO_DEPTH` | 1500FU の天球上。後ろに何も無く、互いに隠れない |
| 2 | スフィアのワイヤーフレーム (現在は 2D) | `NO_DEPTH` | 下記 |
| 3 | エンティティ・破片・弾・エフェクト | — | 従来どおり Z ソート |
| 4 | オーラ・体力警告・マーカー | `NO_DEPTH` | 視点の 1.9〜2.0 前の平面。加算合成で、すでに奥から手前の順 |

12,600 フレームで検証した結果:

- レイヤ 1・3・4 だけの分割は**フレームハッシュが完全に一致**する
  (体力警告は AI 運転では発火しないので、閾値を外して強制発火させた別ランでも確認)。
- **ワイヤーフレームを別レイヤにするのも、深度を残す限り完全に一致する。**
  つまり地表に立つものは必ずワイヤーフレームより手前にあり、
  前後関係はレイヤだけで決まる。
- ワイヤーフレームを `NO_DEPTH` にすると差が出るが、147 フレーム走査での最悪値で
  **57,600 画素中 131 画素、チャンネル差 9/255** (RGB565 の量子化 1 段ぶん)。
  `wireColor()` の色が青一色のランプで、交差する 2 辺は距離もほぼ同じなため。

差が出る向きだけ注意: `NO_DEPTH` は「後に出したものが勝ち」だが、
`subdivideFace()` は**プレイヤーに近い順**に辺を出すので、交差点では遠い=暗い辺が勝つ。
この出力順はライン予算が尽きたとき遠方の面だけが粗くなるようにするためのもので、
逆にはできない。

`NO_DEPTH` の不透明スパンは互いを間引けないので `spanPeak` が 31→34 に増えるが、
容量 451 に対して誤差。逆にスパンごとの深度平面評価とソートが減るぶん、
ホストでの同一 12,600 フレームの所要時間は 3,910ms → 3,760ms (−3.8%) になった。

### 省略している ShapoGFX の機能

b03055e で 3D レンダラの各機能を個別に落とせるようになった。
このゲームで落とせるのは**テクスチャだけ**。240x240・レベル 0〜7 の 10 フレームで
既定ビルドと突き合わせた結果:

| マクロ | 結果 | 判定 |
|---|---|---|
| `SHAPOGFX3D_TEXTURE=0` | **10 フレームとも完全一致** | **採用** |
| `SHAPOGFX3D_GOURAUD=0` | 10 フレームで 8,313 画素が変化 | 不可 (頂点色の補間を使っている) |
| `SHAPOGFX3D_LINES=0` | 10 フレームで 29,490 画素 | 不可 (スフィアのワイヤーフレーム) |
| `SHAPOGFX3D_BLEND=0` | 8 フレームで 140 画素 | 不可 (`BlendMode::ADD` の弾・オーラ) |
| `SHAPOGFX3D_POINTS=0` | 10 フレームで 128 画素 | 不可 (星と遠方のエンティティ) |

`SHAPOGFX3D_STACK_DEPTH` (既定 16、1,088B) と `SHAPOGFX3D_VCACHE_SIZE`
(既定 64、2,304B) はアリーナの固定部を決める。`pushState()` は使っていないので
前者は削れるが、合わせても 3KB 強でアリーナの 3% ほどにしかならないので既定のまま。

**注意: テクスチャを無効にしても、テクスチャ付きのシーンはコンパイルも描画も通る**
(無効な機能のメンバは実行時に無視されるだけ)。将来 core/ 側にテクスチャを足しても
実機では黙って無地で描かれる。WASM 版はこのマクロを付けていないので、
そこだけ見た目が食い違うことになる。

## 帯単位の描画と転送

ST7789 のメモリ書き込みはウィンドウの原点から始まるので、**帯ごとに
`setWindow()` が必要**。`writePixelsStart()` は DMA を開始して即座に返り、
SPI ロックを保持したままになる。`writePixelsComplete()` が完了を待ってロックを解放する。

```
beginFrame(game, dt)
for b in 0 .. 5:
    buf = bands[cur]; cur ^= 1
    renderBand(buf, b*40, 40, 0)     # 直前の帯の DMA と重なる
    drain()                          # 直前の帯の DMA を回収 (start() の中で行う)
    setWindow(0, b*40, 240, 40); writePixelsStart(buf, 240*40*2)
endFrame()
# 最後の帯は転送中のまま抜ける (次フレームの tick と beginFrame に重ねる)
```

設計上の要点:

- **転送中に `setWindow()` や `writePixelsStart()` を呼ぶと復帰不能なハングになる。**
  SPI ロックはバイナリセマフォ上のスピンで、エラーを返さない。
  表示 API に触るのは `BandWriter` だけに限り、`start()` の先頭で必ず `drain()` する。
- **最後の帯は `drain()` せずに抜ける。** 末尾の転送 (2.46ms) を次フレームの
  tick と `beginFrame()` に重ねられるので、フレーム時間が
  `max(CPU 合計, DMA 合計)` に近づく。素直に待つと両者が直列になる。
  これが安全なのは、`system::requestShutdown()` が各種 deinit より**先に**
  `xmcAppTerminate()` を呼ぶため。`xmcAppTerminate()` で `drain()` している。
- **帯バッファの添字はフレームを跨いで連続させる** (フレーム先頭で 0 に戻さない)。
  戻すと、帯数が奇数のときに「前フレームの最後の帯が転送中のバッファへ
  次フレームの帯 0 を描く」競合が起きる。
- 表示 SPI は 62.5MHz なので、全画面 115,200 バイトの転送に 14.75ms かかる。
  これがフレームレートの上限 (約 67fps) を決める。
- SDK の `RGB565` はメモリ上でバイトスワップされており、ShapoGFX の
  `RGB565BE` とビット単位で一致する。変換は不要。

## 2 つのコアの分担

**core1 が sim、core0 が描画**。両ターゲット共通。
狙いは **core1 が次フレームの tick を進めている間に core0 がラスタライズして転送する**こと。

```
core0                                core1
  batch 完了を確認 <---------------  batch 完了
  beginFrame()                        (idle)           ← core1 は待つ
  RUN を発行 (tick 回数 + ボタン) -->  tick x N
  ラスタライズ + 転送          <--->  tick x N (続き)
```

入力は core0 で読んで (`input::service()` が core0 の `libLoop` で回るため)、
tick 回数と一緒に core1 へ渡す。

この向きである理由:

- Xiamocon の core1 は演算に専念させる設計で、ペリフェラルを叩くことは想定されていない。
- **ESP32S3 ではディスプレイが core0 からしか反応しない** (下記参照)。
- 逆向き (core1 が描画) も一度実装したが、core0 側で tick と `beginFrame()` が
  直列に並ぶため、RP2350 で測っても速くならなかった。

**1 フレーム分の入力遅延が出る**。描くのは core1 が進め終わった状態で、
いま読んだボタンは次のフレームに効く。重ねる以上これは避けられない。

`DS_SIM_ON_CORE1=0` で全部 core0 に寄せられる。遅いが、問題が分割由来かを
切り分けるのに使える。

### 待ち方

core1 が tick 中のとき、core0 は**スピンせずに `xmcAppLoop()` から戻る**。
core0 は `system::service()` を回す唯一のコアで、そこが止まると
電源ボタンも IO エクスパンダのサービスも止まるため。

### 共有データの分離

batch が走っている間、どちらのコアが何に触るか:

| core0 (描画) | core1 (sim) |
|---|---|
| アリーナと構築済みシーン、帯バッファ、ディスプレイ、`Renderer` の HUD スナップショット・ゲージ・マーカー | `Game`、および `pollEffects()` が書く `Renderer` のエフェクト状態 (デブリ、取得フラッシュ、エフェクト用 rng) |

この分離が成り立つのは `renderBand()` が `Game` を参照しなくなったから
(core/SPEC.md の `HudState` 参照)。エフェクト状態は `renderBand()` からは読まれない。
`beginFrame()` は `Game` 全体を読むので、batch を回収してから次を依頼するまでの
core1 が idle な区間で走る。

受け渡しは 32 ビット 1 語を `__atomic_load_n` / `__atomic_store_n` の
acquire/release で行う。`std::atomic` は Xtensa で lock-free 保証にならず、
`xmc::Semaphore` は実体がバイナリミューテックスなので、どちらも使わない。

### core1 が起動したかは自分で確かめる

**`xmc::startCore1()` は `xTaskCreatePinnedToCore()` の戻り値を見ずに `XMC_OK` を
返す** (ESP32S3 の場合)。スタック 8KB は帯バッファと同じプールから取るので、
アリーナを大きくしすぎると黙って起動しない。起動後に少し待って、
core1 が実際に走ったかを確認している。

## ゲームループ

`xmcAppLoop()` の 1 回の呼び出しが 1 フレームに対応する。

- `getTimeUs()` の差分をアキュムレータに足し、`1000000/60` µs ごとに `game.tick()` を進める。
  1 フレームあたりの追いつきは 4 tick まで。経過時間はアキュムレータに入れる前にも
  後にもクランプするので、長時間停止から復帰してもシミュレーションがバーストしない。
- tick が 1 回以上進んだフレームだけ描画する。描画がシミュレーションより速いときは
  同じ絵を描き直さずに抜ける。
- **tick ごとに `Renderer::pollEffects()` を呼ぶ。** エフェクトのイベントは tick ごとに
  クリアされるので、1 フレームに 2 tick 進むときこれを怠るとフレーム内の最後の tick
  以外の爆発やデブリが出ない。
- `beginFrame()` に渡す `dt` は実経過時間ではなく `ticks / 60` 秒。レンダラはカメラの
  補間・デブリ・スコアのロールアップをこの値で進めるので、実際に進んだ tick と
  揃えないと演出だけがシミュレーションより先に進む。
- **`beginFrame()` から最後の `renderBand()` までの間にシミュレーションを進めてはいけない。**
  `renderBand()` は HUD を描き、HUD は生きた `Game` を読む。
- ボタンの押下エッジは追いつき tick を跨いでも壊れない
  (`Game::tick()` が `pressed = buttons & ~prevButtons_` を計算するので、
  4 tick 押しっぱなしでも押下イベントは 1 回)。

ホストで同じアキュムレータを回した結果 (600 フレーム):

| 描画レート | シミュレーション時間 / 実時間 | tick/フレームの内訳 |
|---|---|---|
| 60fps | +0.2% | 1x599, 2x1 |
| 50fps | +0.1% | 1x479, 2x121 |
| 40fps | +0.1% | 1x299, 2x301 |
| 30fps | +0.1% | 2x599, 3x1 |
| 100fps | +0.3% | 0x239 (描画せず), 1x361 |
| 15fps | -0.0% | 4x600 (追いつき上限ちょうど) |
| 10fps | -33% | 4x600 (上限を超え、スローモーションになる) |

15fps までは実時間を保つ。それより遅いとゲームがゆっくりになるが、
追いつきを増やして取り戻そうとするよりはこちらの方が破綻しない。

## 実機での性能

**この節の実測値はすべて ShapoGFX 8eff034 (レンダラの高速化) より前のもの。**
あの変更は RP2350 級の的を絞って `BGN` (三角形ごとの平面セットアップ) と
`RAS` (スパンあたりの除算と分岐) を削っているので、実機で測り直す価値がある。
x86 ホストでは差が出ない (このゲームはテクスチャを使わず、x86 の除算は安いため)
ので、数字は実機でしか得られない。
`TRI` の容量は下記のどの数字よりも約 6% 大きくなっている (「アリーナの大きさ」参照)。

初回計測 (レベル 1、タイトルのデモ、`TICK_RATE=60`):

```
FPS 21.5  TCK 19.85x3      1 フレームに 3 tick、1 tick あたり 6.6ms
BGN 10.35  RAS 9.15
DMA 7.79  CPU 39.36        フレーム 46.5ms = CPU 39.36 + DMA 待ち 7.79
```

x86 との比は TCK 91 倍、BGN 112 倍、RAS 68 倍。クロック比だけで 18 倍あり、
そこに in-order 実行・SIMD 無し・XIP フラッシュ実行が乗る。

CPU が 39.4ms で DMA の下限 14.75ms を大きく超えており、**完全に CPU 律速**。
内訳の半分が tick で、しかもフレームあたり 3 回回っていたので、
`TICK_RATE` を 30 に落とした。
その後コア分割 (`core1` が描画) によって tick が描画の陰に隠れるようになったため、
60Hz に戻している (ビルドは `DEVOURSPHERE_TICK_RATE=60`)。

計算上は `フレーム時間 = (T/33.3)*6.62 + 10.35 + 9.15 + 7.79` を解いて
**T ≈ 34ms (約 29fps)**。この式は 60Hz の実測値をそのまま再現するので信頼できる
(3*6.62 + 10.35 + 9.15 = 39.36 = 実測の CPU)。

### バランスへの影響

`sim_bench` 相当を 9 シード x 3 武器 x 120 秒で回した中央値:

| | 60Hz | 30Hz |
|---|---|---|
| 命中率 | 64.3〜65.0% | 63.2〜64.5% |
| 撃破/分 | 85〜87.5 | 93.5〜94 |
| 取得/分 | 985〜996 | 989〜1019 |
| 120 秒での死亡 | 3,4,3 / 9 | 2,4,4 / 9 |

命中率が変わらないことが重要で、弾速の最も速いレーザー (30Hz で 1 tick 8 FU) でも
すり抜けは起きていない。撃破数だけ +8% だが、死亡率と餌の取得ペースは同等。

### これ以上速くするには

BGN + RAS = 19.5ms はフレームレートに依らない固定費なので、
シングルコアでの上限は約 36fps。それを超えるには:

- **デュアルコア化**: core1 が `beginFrame()` + ラスタライズ (19.5ms)、
  core0 が tick と DMA 投入。フレームは `10.35 + 9.15 + 転送の端数` で約 21ms、
  **45fps 前後**が見込める。ただし `renderBand()` が `drawHud()` 経由で生きた `Game` を
  読んでいるため、`beginFrame()` 時点でのスナップショット化が前提になる。
  また core0 が tick できるのはラスタライズ中の 9.15ms だけ (`beginFrame()` は
  `Game` 全体を読むので止める必要がある)。
- **ホットコードを RAM に置く**: コードは QSPI フラッシュから XIP キャッシュ越しに
  実行されており、gfx3d のスパンループはその最悪ケース。`copy_to_ram` (全体) は
  `.text` + `.bss` が 512KB を超えるため使えないが、gfx3d + gfx2d + render だけなら
  約 65KB で空き RAM に収まる。

## 2 つのターゲットの違い

コアの分担もフレームループも共通で、`#if defined(ESP32)` で分けているのは
次の 5 点だけ。

| | RP2350 | ESP32S3 |
|---|---|---|
| `TICK_RATE` | 60 | **30** |
| 帯の高さ | 40 行 (6 帯) | **80 行 (3 帯)** |
| `sim::Game` (136KB) | `.bss` | **PSRAM** (`MALLOC_CAP_SPIRAM`) |
| 帯バッファ | アラインした静的領域 | **DMA ヒープ** (`MALLOC_CAP_DMA`) |
| 乱数シード | `get_rand_32()` (pico-sdk) | `esp_random()` |
| スタック計測 | スタックを塗って走査 | `uxTaskGetStackHighWaterMark()` |
| 失敗時のトレース | 無し (シリアル未設定) | `Serial` (USB CDC) |

ESP32S3 はリンカがアプリに **320KB** しか与えない。`Game` を PSRAM に追い出して
内部 DRAM を 136KB 空け、残りからアリーナ (静的) と、帯バッファ・SPI ドライバの
バッファ・各タスクスタック (実行時) を取る。
かつてはアリーナが 128KB だと core1 のスタック 8KB が取れずに黙って起動しなかったため
96KB に削っていたが、**ShapoGFX の 3 段階の改善で両ボードとも 64KB になり、
この差は無くなった** (「アリーナの大きさ」参照)。
PSRAM 上の tick は 11.8ms で、RP2350 (内部 SRAM, 250MHz) の 7.4ms に対して
6 割増しに留まる。

実測: **RAM 108,908 / 327,680 (33.2%)** (帯バッファは実行時にヒープから取るので
この数字には入らない)、Flash 約 606KB / 3,342,336 (18.1%)。
ヒープに残るのは 218KB で、96KB アリーナだった頃の 178KB より 40KB 多い。

60Hz・6 帯のときの内訳 (core0 単独、14.0fps = 71ms):

```
FPS 14.0   TCK 38.23x4      追いつき上限の 4 tick に張り付き。1 tick 9.6ms
BGN 6.03   RAS 10.89
DMA 10.63  CPU 31.98
CMD 4.41   W 0.00           RP2350 の 0.26ms に対して 17 倍
XFR 27.47                   全画面転送。理論値 (60MHz で 15.4ms) の 1.8 倍
```

ここから 2 つ削っている。

- **`TICK_RATE` を 30 に**。tick がフレームの 54% を占め、しかも追いつき上限に
  張り付いていた。RP2350 がシングルコアだったときと同じ状態。
- **帯を 6 本から 3 本に**。ESP32 では 1〜5 バイトのコマンドも
  「別タスクへキュー投入」の DMA パスを通るので、帯ごとの `setWindow` が高い。
  帯を減らせば `CMD` も帯ごとの待ちも減る。RAM を 38KB 多く使う。

その後 sim を core1 に移して重ねた。最終的な数字 (29.9fps = 33ms):

```
FPS 29.9   TCK 11.78x1      core1 で回るので core0 の 28.52ms に隠れる
BGN 6.18   RAS 10.14
DMA 9.92   CPU 28.52        core0 のクリティカルパス
TRI 140/500 d0              当時の容量。ba15719 以降はバイト表示になっている
CMD 2.27   W 0.00           core0 は core1 を待っていない = 重なっている
XFR 25.37
STK1 2124  STK0 3552
```

`TICK_RATE` が 30 なので tick 周期 33.3ms が上限。core0 が 28.5ms なので
そこに張り付いている。

### `Game` を DRAM に置くのは無理 (実機で確認済み)

`Game` を内部 DRAM に置く構成は**試したが起動しなかった**。同じ道を辿らないこと。

DRAM の予算は 327,680 バイトしかなく、`Game` だけで 136KB ある。
当時はアリーナを 128→48KB、帯を 3 本→6 本に戻せばリンクは通った
(237,028 = 72.3%) が、残ったヒープでは**帯バッファ (38KB) と
SPI の DMA バッファ (32KB) を確保しきれず起動に失敗した**。

アリーナが 64KB になった今でも結論は変わらない。静的が 116,916 なので
`Game` を足すと 253,428、ヒープに残るのは 74,252 バイトで、
**80 行帯のバッファ 2 枚 (76,800) だけで既に入らない**。
帯を 6 本に戻せば 38,400 で収まるが、そのぶん `CMD` が 2.27→4.41ms に戻る。
PSRAM 上の tick は 10.05ms で、RP2350 (SRAM, 250MHz) の 7.4ms に対して 36% 増しに
留まっているので、PSRAM の代償はもともと小さい。得るものが無い。

その他の注意:

- コア間の受け渡しは `std::atomic` ではなく `__atomic_load_n` /
  `__atomic_store_n` の acquire/release を使う。**Xtensa のツールチェーンでは
  `std::atomic<uint32_t>` が lock-free 保証にならず**、ロックを取る実装になると
  別コア間では正しく動かない。32 ビットのアラインされた load/store はどちらの
  ターゲットでも不可分なので、ビルトインが足すのはバリアだけ。
- ESP32S3 の `getTimeUs()` は `micros()` で、約 71 分で 32 ビットが一周する。
  フレームループは経過時間をクランプしているので、一周しても 1 フレーム分の
  遅れが出るだけで破綻はしない。
- `startCore1()` は `xTaskCreatePinnedToCore(..., 8192, ..., PRO_CPU_NUM)` で、
  Arduino の `loop()` は APP_CPU なので物理的に別コアになる。スタックは 8KB。
- 表示 SPI は 60MHz (RP2350 は 62.5MHz)。
- core と ShapoGFX は PlatformIO のライブラリとして参照する
  (`core/library.json` と `submodule/shapo-gfx/library.json`)。
- 起動時の進行状況を `ds::trace()` がシリアルに出す
  (`pio device monitor -b 115200`)。PSRAM と帯バッファのアドレス、転送の実測、
  どちらのコアで描画するか。RP2350 では何もしない。
  画面が出ない状態を調べる唯一の窓口なので残してある。

### ESP32S3 で core1 描画を切っている理由

**ESP32S3 では core1 からディスプレイを叩くと画面が出ない。** 切り分け済み:

- シーンは正しく作られている (`tri` 187/676、`lines` 336、`raster us` 3267、
  `state` と tick も正常に進み、アトラクトの AI でプレイヤーが成長する)
- **setup 中に core0 から出した転送はパネルに届く**
  (未初期化の帯バッファが砂嵐として一瞬映る)
- **core1 から出した転送は届かない** — 画面は黒のまま
- 同時に電源ボタンも効かなくなる (FUNC 起動の診断アプリでは効く)
- core0 で描くようにすると、**表示も電源ボタンも正常になる**

つまり転送経路もフレームの中身も正しく、core1 (FreeRTOS タスク) から
ディスプレイを叩いたときだけ効かない。
そのため両ターゲットとも core0 が描画し、core1 が sim を回す (上記「2 つのコアの分担」)。

疑っている原因 (未検証): ESP32 側の `spi::dmaWriteStart` は
`ESP32DMASPI::Master` の内部タスク経由で転送する。一方 `xmc::startCore1` が作る
タスクは優先度 10 で PRO_CPU に固定され、暇なときも `tightLoopContents()` で
回り続けるので、同じコアに載った SPI の内部タスクを飢えさせている可能性が高い。
電源ボタンが効かなくなるのも、同じコアの他のタスクが動けていない兆候として
辻褄が合う。RP2350 には該当しない (あちらは DMA を直接叩く)。

直すなら core1 のアイドル時に `vTaskDelay(1)` を入れる、もしくは SPI の内部
タスクを APP_CPU に寄せる (SDK 側の変更) あたり。

## 入力

| 操作 | ボタン |
|---|---|
| 左右旋回 | LEFT / RIGHT |
| ダッシュ | UP |
| ブレーキ | DOWN |
| A (攻撃・決定) | A / B / X / Y のどれでも |

- `input::service()` は自分で呼ばない。`libLoop()` の `system::service()` が
  毎回呼んでおり、二重に呼ぶと `wasPressed` / `wasReleased` のエッジが壊れる。
- 入力はフレームの先頭で `input::getState()` を 1 回だけ読む。
- FUNC は起動時のみ SDK が特別扱いする (押しながら起動すると内蔵の診断アプリになる)。
  実行中は自由に使える。

## デバッグ表示

実行中に FUNC を押すと、直前のフレームの計測値を画面左上に重ねて表示する。

```
FPS 41.3  TCK 1.24x1      フレームレート / tick の所要時間 x 進めた tick 数 (core0)
BGN 2.61  RAS 8.40        beginFrame / 帯のラスタライズ合計 (core1)
DMA 4.02  CPU 12.25       DMA 完了待ち / core1 のクリティカルパス (BGN+RAS+DMA+CMD)
TRI 255 16/53K d0         三角形数 / バッファの使用量と総量 (KB) / 取りこぼし
SPN 33 d0 ARN 22K         スパンのピークと取りこぼし、アリーナの実使用量
CMD 1.85  W 0.30          帯ごとの setWindow + 転送開始 / core0 が core1 を待った時間
STK1 2592  STK0 2340      各コアのスタック最大使用量 (バイト、どちらも上限 4096)
```

- **表示は常に 1 フレーム遅れ**。そのフレームのラスタライズ時間は、
  それを描いている最中には出せない。`BGN` はさらにもう 1 フレーム遅れる
  (整形するのが `beginFrame` の完了を待つ前だから)。
- `CMD` は帯の本数に比例する固定費。実機では 0.26ms しかないので、帯を減らしても意味はない。
- `W` が 0 なら core1 は律速ではない (フレームレートを決めているのは tick レートか core0)。
- `STK1` / `STK0` はどちらも上限 4096。**スタックは SCRATCH_X / SCRATCH_Y にあり拡張できない**ので、
  ここが 4096 に達したら本当に溢れている。`MAX_ENTITIES` 個の配列をローカルに置くだけで届く
  (core/SPEC.md のメモリの項を参照)。
- **シーン構築側のスタックは毎回動くので、更新のたびに見ること。**
  `-fstack-usage` で最深経路 (`beginFrame` → `buildScene` → `buildSphere` →
  `traverseSphere` → `subdivideFace` x7 → `emitEdge` → `emitChord` →
  `putLine3` → `putPrimitive`) を足し上げた値と、実機の `STK0`:

  | | 最深経路 (静的) | `STK0` 実測 RP2350 | 同 ESP32S3 |
  |---|---|---|---|
  | 8eff034 より前 | 2,272 | | |
  | 8eff034 | 2,440 | | |
  | b03055e | 2,528 | | |
  | ba15719 | 2,736 | 2,532 | 3,540 |
  | ワイヤーフレーム書き換え後 (現在) | **2,596** | **2,340** | **3,252** |

  ESP32S3 が静的見積りより 650〜800 バイト多いのは FreeRTOS のタスク切り替えと
  Xtensa のレジスタウィンドウのぶんで、**2 つのボードのうち常にこちらが細い**
  (残り 844 バイト)。静的見積りの増減は実測にそのまま出るので、
  更新のたびに見る値としては使える。

  b03055e の +88 は、`VertexBuffer` が 8→36 バイトになった (`packed` /
  `scale` / `bias` が付いた) ぶんが主。このゲームは `VertexBuffer` を
  ローカルに置く箇所が 9 つあるので、そこがそれぞれ 24〜48 バイト太っている。
  ba15719 では `putPrimitive()` が 280→256 バイトに減って初めて下がった。
  ワイヤーフレームの書き換えでは `subdivideFace()` が 216→232 バイトに増えたが、
  弦の分割を再帰ではなくループにし (`emitSplitEdge()`)、`traverseSphere()` から
  `emitIcoEdges()` を分けて再帰中に生きるフレームを 32 バイトに抑えたので、
  差し引き 140 バイト縮んだ。実測では RP2350 で 192、ESP32S3 で 288 減っている。
- `CPU` が 14.75ms (全画面転送に要する時間) を超えているかどうかが、
  フレームレートを決めているのが CPU 側か表示側かの判断材料になる。
- `d0` 以外 (取りこぼしあり) が出たらアリーナが足りていない。
- このボードにはシリアルコンソールが無く (SDK は USB stdio を有効にせず
  `stdio_init_all()` も呼ばない)、有効にすると USB の割り込みが
  まさに計測したいフレーム時間を乱すので、画面に出している。
- 数値の整形は整数演算だけで行う。newlib の `%f` は約 10KB を引きずり込み、
  数百 µs かかるので計測を歪める。
- パネルは帯の境界を跨ぐが、クリップ矩形が行を 2 つの帯に分けるので継ぎ目なく出る。
- `-DDS_PROFILE=0` でコードごと消せる。

## 起動時の注意

- `xmcAppGetConfig()` は `display::init()` **より前**に呼ばれるので、そこで表示に触らない。
- 乱数のシードは pico-sdk の `get_rand_32()` を使う。
  `xmc::randomU32()` はシードされていない newlib の `rand()` で、毎回同じ列になる。
