# Devour Sphere (M5Tab5 版)

[M5Stack Tab5](https://docs.m5stack.com/en/core/Tab5) (ESP32-P4 の 5 インチタブレット型開発機)
で core/ を動かすためのファームウェア。ゲームのルールと描画はすべて core/ 側にあり、
ここには「実機へのビルド」「表示への転送」「タッチ入力」「音」だけがある。

M5Unified / M5GFX は**足回りだけ**を借りる (DSI パネルの起動、タッチ、スピーカー、電源)。
描画は core/render の `Renderer::renderBand()` + ShapoGFX で行い、M5GFX の描画 API は使わない。
Xiamocon 版が Xiamocon SDK と結んでいるのと同じ取り決め。

## 必須要件

- 画面は横長で使う。パネルは **720x1280 の縦長**なので、毎フレーム 90 度回す必要がある。
- ゲームは **640x360** のランドスケープのフレームに描き、PPA が 2 倍拡大・90 度回転・
  バイト入れ替えを 1 回の操作でまとめてパネルのフレームバッファへ書く。
- フレームバッファを 1 枚も持たず、45 行の帯を 2 枚交互に使って描画・転送する
  (パネル側のフレームバッファは DSI のもので、こちらは書くだけ)。
- シミュレーションは 60Hz 固定、描画は追いつける範囲で行う (可変フレームレート)。
- 入力は WASM 版の横画面と同じ仮想パッド (方向ディスク + A + B) と、ポーズボタン。
- 効果音は M5Unified のスピーカーで**多重発音**する (ハンドヘルドの 1 音 + 優先度ではなく、
  ブラウザ版と同じ鳴り方)。
- ハイスコアは NVS に保存する。
- プラットフォームは **ESP-IDF v5.5.x** (Arduino / PlatformIO ではない)。

## ビルドと書き込み

```sh
cd impl/m5tab5/devoursphere
./build.sh                       # DS_IDF_PATH 既定 ${HOME}/esp/5.5
./run.sh /dev/ttyACM0            # ビルドして書き込み (ポート省略可)
./monitor.sh                     # シリアルログ
```

- **ESP-IDF v5.5.x が必要**。PPA のドライバ (`esp_driver_ppa`) は 5.4 以降にしかなく、
  M5GFX / M5Unified の ESP-IDF ビルドは 5.5 系までしか検証されていない (6.0 は不可)。
- `DS_IDF_PATH` は ESP-IDF を置いたディレクトリ (その下に `esp-idf/` がある)。
  3 つのスクリプトすべてで同じ既定値を使う。
- 初回は `idf.py set-target esp32p4` が要る (build.sh は呼ばない。
  `sdkconfig.defaults` に `CONFIG_IDF_TARGET` があるので `idf.py build` でも設定される)。
- `managed_components/` と `sdkconfig` は生成物なので git 管理外。

### sdkconfig.defaults

ボード固有の値は LcdTap の M5Tab5 サンプル (`~/repo/2026/lcdtap/example/m5tab5`) で
実機検証済みのものをそのまま使っている:

| 設定 | 理由 |
|---|---|
| `SPIRAM_MODE_HEX` + `SPIRAM_SPEED_200M` | パネルのフレームバッファが PSRAM にあり、DSI が常時読み続ける。ここが遅いと絵が出ない |
| `CACHE_L2_CACHE_256KB` / `LINE_128B` | 同上。内蔵 SRAM 768KB のうち 256KB がキャッシュに取られる |
| `ESP_DEFAULT_CPU_FREQ_MHZ_400` | |
| `COMPILER_OPTIMIZATION_PERF` | フレーム時間は ShapoGFX のスパンループと IDF の PPA / キャッシュ経路に消えるので、自分の翻訳単位だけ -O2 にしても効かない |
| `ESP_CONSOLE_USB_SERIAL_JTAG` | Tab5 は USB-C しか出ていない |
| `ESP32P4_SELECTS_REV_LESS_V3` / `REV_MIN_0` | IDF 5.5 の既定はチップリビジョン v3.1 以上。実機は v1.0 を返すので、無いとブートローダが起動を拒否する |
| `ESP_MAIN_TASK_STACK_SIZE=16384` | `app_main` のタスクがシーン構築とラスタライズをする。`buildSphere()` は 7 段再帰する。既定の 3584 では足りない |
| `ESP_TASK_WDT_INIT=n` | 2 つのコアがそれぞれ専有して回るので、アイドルタスクが回らないコアで発火してしまう |

## 画面: 座標系と PPA

ここがこの移植の中心なので先に書く。

```
ゲームが描くもの  640x360 のランドスケープ、RGB565 ビッグエンディアン
パネル            720x1280 の縦長ラスタ、RGB565 リトルエンディアン、
                  DSI が常時走査している
```

M5GFX の回転 1 はランドスケープの画素 (u, v) をパネルの画素 (719 - v, u) に写す。
これは**ランドスケープの絵を時計回りに 90 度回す**操作で、PPA の角度は反時計回りなので
`PPA_SRM_ROTATION_ANGLE_270` になる。表示に設定するのと同じ回転を使うことが、
`M5.Touch` の座標が自分で描いたパッドの上に乗ることを保証している。

帯 b は拡大後のランドスケープの行 `[v0, v0 + 2*BAND_H)` を占め、上の写像の下で
パネルの縦帯 `X ∈ [720 - v0 - 2*BAND_H, 720 - v0)`、`Y` は 1280 行すべて、になる。

1 回の `ppa_do_scale_rotate_mirror()` で次を同時に行う:

- 拡大 2 倍 (`scale_x` / `scale_y`)
- 回転 90 度 (`rotation_angle`)
- **バイト入れ替え (`byte_swap`)**。これのおかげで ShapoGFX は他のターゲットと同じ
  `RGB565_SWAPPED` を描き続けられる。画素をなめ直す変換は一切要らない。

`PANEL_ROTATION` (ds_config.hpp) は 1 か 3。**表示・PPA の角度・帯のオフセットが
すべてこの 1 つの値から決まる**ので、上下が逆さまに出たらここだけ直せば
絵とパッドが同時に追従する。どちらが正しいかはパネルの取り付け方で決まり、
ソフトウェアからは分からない。**実機は 3** (2026-09-20 に確認。1 では上下が逆だった)。

### 帯の ping-pong

```
beginFrame(game, dt)
for b in 0 .. 7:
    buf = bands[cur]; cur ^= 1
    renderBand(buf, b*45, 45, 0)     # 直前の帯の PPA と重なる
    パッドと計測オーバーレイを重ねる
    drain()                          # 直前の帯の PPA 完了を待つ
    submit(buf, b*45)                # 非ブロッキング、完了はコールバックでセマフォ
endFrame()
# 最後の帯は転送中のまま抜ける (次フレームの tick と beginFrame に重ねる)
```

- **帯バッファの添字はフレームを跨いで連続させる** (フレーム先頭で 0 に戻さない)。
  帯数が奇数のときに、戻すと「前フレームの最後の帯が転送中のバッファへ
  次フレームの帯 0 を描く」競合が起きる。Xiamocon 版と同じ理由・同じ対処
  (今の 45 行では 8 帯で偶数だが、`BAND_H` を変えても壊れないようにしてある)。
- 帯バッファは**内蔵 SRAM**に置く。PPA の読み出しが、自分の書き込み先であり
  DSI が走査中でもある PSRAM と同じバスを取り合わないようにするため。
- PPA はバスマスタとして読むので CPU のデータキャッシュを見ない。投入前に
  `esp_cache_msync()` で書き戻す。バッファは L2 のラインサイズにアラインして確保する
  (内蔵メモリでもドライバはこのアラインを要求する)。
- 起動時に M5GFX がキャッシュ経由でフレームバッファに描いた分を、パイプラインを
  始める前に 1 回 msync しておく。後から書き戻されて PPA の結果を上書きしないように。
- `num_fbs = 1` (M5GFX の Panel_DSI がそう作る) なのでダブルバッファではなく、
  ティアリングはある。ただし帯 = ランドスケープの横帯なので、Xiamocon 版と同じ
  「上から順に更新される」見え方になる。

## 解像度を 640x360 にした根拠

ホストで同一シーンを 200 フレーム描いてフェーズ別に測った (ms):

| 解像度 | beginFrame | 帯 3D | 帯 2D+HUD | 合計 |
|---|---|---|---|---|
| 240x240 | 0.035 | 0.008 | 0.018 | 0.062 |
| 480x320 | 0.079 | 0.012 | 0.045 | 0.135 |
| **640x360** | 0.073 | 0.013 | 0.049 | **0.135** |
| 1280x720 | 0.084 | 0.033 | 0.120 | 0.238 |

**シーン構築は解像度にほとんど依存せず** (0.073 → 0.084)、増えるのは帯の作業だけ。
画素 4 倍に対して x86 では 2.5 倍だが、x86 のような広いストアを持たない CPU では
4 倍に近づく。ESP32S3 (240MHz、240x240 で `RAS 10.14ms`) から外挿すると
1280x720 は 100ms/フレームの桁になる。

HUD の物理的な大きさは**どちらでも同じ**になる: 1280x720 では `UiMetrics::fontMult` が
2 になってビットマップフォントが 2 倍にドット拡大されるだけで、640x360 + 2 倍拡大と
文字の大きさは変わらない。違うのは「ドット拡大かバイリニア拡大か」だけ
(PPA の SRM は内部でバイリニア補間する)。ホストで再現して見比べた限り、
ワイヤーフレームの線はむしろ滑らかになる。

2 倍という比率も効いている。PPA の拡大率は 1/16 刻みなので他の比率も取れるが、
1280 と 720 を整数で割り切れるのは 2 倍 (640x360) と 4 倍 (320x180) だけ。

## メモリ配分

ESP32-P4 の内蔵 SRAM は 768KB、うち 256KB が L2 キャッシュ。リンカが見る DIRAM は
**445,392 バイト**。

| 用途 | サイズ |
|---|---|
| `.bss` (`sim::Game` 84KB + アリーナ 48KB + `Renderer` 24KB + IDF / M5 ほか) | 178,864 (アリーナを 32KB にした現在は約 16KB 少ない) |
| `.text` (IRAM) + `.data` | 98,830 |
| **静的の合計** | **277,694 (62.4%)** |
| 残り (ヒープ) | 167,698 |

ヒープから実行時に取るもの:

| 用途 | サイズ |
|---|---|
| 帯バッファ 640x45 x2 | 115,200 |
| `app_main` のスタック | 16,384 |
| sim タスクのスタック | 8,192 |
| M5GFX / タッチ / I2S / FreeRTOS ほか | 残り約 40KB |

**帯の高さがここで決まっている**。実機で **45 行 (115KB) まで**。
**60 行 (150KB) は画面が真っ暗になる** — 帯バッファが確保できずに `init()` が諦めた状態で、
シリアルにはそう出ている。足りないのは**内蔵ヒープの合計ではない** (その時点で 246KB ある)。
帯バッファは 1 つの**連続した**ブロックでなければならず、内蔵ヒープは複数の領域に
分かれているので、合計に余裕があっても 1 つの領域が 76,800 バイトを収められない。
起動時とエラー時に「合計」と「最大の連続ブロック」の両方を出すのはこのため。

40 行 (100KB) で測った実機の値: 起動直後の内蔵ヒープ **246,231 バイト**、
すべて確保した後 **134,783 バイト** (2026-09-20)。

`sim::Game` は**内蔵 SRAM に置く** (ESP32S3 版は PSRAM に追い出さざるを得ないが、
こちらは 84KB を出す理由がない)。

### アリーナの大きさ

640x360 で、レベル 1〜7 × 3 シード × 600 tick を AI に回した 12,600 フレームの
**全フレームをハッシュ**して比較した。ShapoGFX d538138 (スパン 68 → 16B、レコード縮小) 以降の値
(サイズは同じ run を 32 ビットの wasm でビルドして取った):

| アリーナ | 三角形バッファ | ピーク使用 | 結果 |
|---|---|---|---|
| 48 KB | 42,168 B | 9,984 B | 一致 |
| **32 KB** | 25,784 B | 9,984 B | 一致 (**採用**) |
| 24 KB | 17,592 B | 9,984 B | 一致 (**変曲点**) |
| 20 KB | 13,496 B | 9,828 B | エンティティが細部を失い始める |
| 16 KB | 9,400 B | 9,396 B | 取りこぼしあり |

24KB が `buildScene()` が要求どおり取れる下限。**32KB** はそこから 3 割、
ピークの 2.6 倍の余裕を残しつつ、内蔵ヒープに 48KB 時代より 16KB 多く返す
(そのヒープが帯バッファの出どころで、このボードで唯一足りないもの)。

それ以前 (ShapoGFX 88d2bb5 まで) は変曲点が 40KB で、アリーナは 48KB だった:

| アリーナ | 三角形バッファ | ピーク使用 | 結果 |
|---|---|---|---|
| 64 KB | 49,824 B | 14,864 B | 一致 |
| 48 KB | 33,440 B | 14,864 B | 一致 |
| 40 KB | 25,248 B | 14,864 B | 一致 (変曲点) |
| 32 KB | 17,056 B | 13,952 B | エンティティが細部を失い始める |
| 24 KB | 8,864 B | 8,864 B | 239 プリミティブ取りこぼし |

スパンプールは 128 (`SPAN_CAPACITY`)。640x360 の実測ピークは 33、1280x720 でも 36。

## 2 つのコアの分担

**core1 が sim、core0 が描画**。両ハンドヘルドと同じ。core0 は batch を投げてから
前の batch が残した状態を描くので、tick は帯が出ていく裏で進む。

受け渡しは**タスク通知 2 本** (`ulTaskNotifyTake` / `xTaskNotifyGive`)。
ポーリングだと、スピンすれば core0 のコールバックを飢えさせ、スケジューラの
tick で眠れば 1kHz でも 1 フレームのうちの無視できない時間を 2 回捨てることになる。
通知はペイロード (tick 数・ボタン・結果) に必要なバリアも兼ねる。

**入力はできるだけ遅く読む**: 待ちの後、シーン構築の後。そのボタンは
「このフレームをラスタライズしている間に走る batch」に渡るので、画面に出るのは
次のフレーム。**この 1 フレームの遅延は重ねる以上避けられない**が、それより前の分は
避けられる。

`DS_SIM_ON_CORE1=0` で全部 core0 に寄せられる (遅いが、問題が分割由来かの切り分け用)。

## 入力

| 操作 | 仮想パッド |
|---|---|
| 左右旋回 | 方向ディスクの左右 |
| ダッシュ / ブレーキ | 方向ディスクの上 / 下 |
| A (攻撃・決定) | 右下の A ボタン |
| B (緊急回避) | A の左上の小さい丸 |
| ポーズ / 再開 | 右上隅のポーズボタン |
| ミュート切り替え | タイトル / ポーズ画面でディスクの下 (core が処理する) |
| 計測オーバーレイ | タイトル / ポーズ画面でディスクの上 |

- 配置とサイズは WASM 版の横画面レイアウト (play.js と play/index.html) をそのまま
  持ってきた: ディスク 150px、A 96px、B 72px を 360px の高さに対して。
  このパネルでは 25.6 / 16.4 / 12.3 mm になる。
- **ディスクは十字キーではない**。タッチ位置と中心のオフセットから左右と上下を
  独立に判定するので、斜め入力 (ダッシュしながら旋回、ブレーキしながらクイックターン)
  ができる。しきい値は play.js のもの (デッドゾーンは半径の 24%、軸ごとはその 7 割)。
- **各コントロールは押した指を捕まえる** (web の pointer capture と同じ)。
  一度ディスクに乗せた指は、外へずれても離すまでディスクを操作し続ける。
  見ずに操作できるのはこれがあるからで、1 本の指が同時に 2 つを持つことはない。
- ポーズは押下エッジだけを渡す (押しっぱなしだと毎 tick トグルしてしまう)。
- パッドの描画は**帯バッファに 640x360 の座標系で** ShapoGFX の 2D で行う。
  PPA が他と一緒に拡大するので、追加の PSRAM 書き込みは無い。
- 半透明 (不透明度 140/255) で重ねる。輪郭は 1 画素 (拡大後 2 画素) にしてある:
  半透明の輪郭を 2 重に描くと重なった所だけ 2 回合成されてまだら模様になる。

### HUD の安全域

`Renderer::setHudInsets()` (core/SPEC.md) にパッドの占める分を渡す。
左右のインセットは**下端の行にだけ**効くので、アップグレードのアイコン・予備コア・
バージョン・操作ヒントがディスクと A の間に収まり、上端の行 (体力ゲージ、スコア、
残り時間) はフレームいっぱいのまま。上のインセットはポーズボタンの分。

## 効果音

ハンドヘルドは 1 音 + 優先度だが、**ここは多重発音**にしている。
M5Unified のスピーカーが ES8388 で 8 チャンネルをミックスするので、
1 音に絞る理由が無い。ブラウザ版と同じ鳴り方 = ゲームを調整したときの鳴り方になる。

- パックは `docs/play/se.bin` (ブラウザ版と同じ。24kHz モノラル s16le、コミット済み)。
  `main/CMakeLists.txt` の `target_add_binary_data()` でフラッシュに置き、
  メモリマップされているので `playRaw()` がその場で読める。
  素材を変えたら `make -C impl/wasm se` で作り直す。
- `playRaw(..., channel = -1)` は空いているチャンネルを探し、8 本とも塞がっていれば
  false を返す。9 個目が落ちても 8 個鳴っている中では聞こえないので、それでよい。
- ミュートは `audio::setMuted()` が `M5.Speaker.stop()` を呼び、以後の要求を捨てる。
- 音量は `SE_MASTER_VOLUME` (ds_config.hpp)。M5Unified のミキサはマスタ音量を**二乗**して
  掛ける (`gain = magnification * master^2 * channel^2`) ので、既定の 64 は中間値ではない。
  111 = 64 x √3 で既定の 3 倍の音量。出力は 16 ビットで飽和する (巻き込まない) ので、
  これ以上上げるとピークが潰れるだけで破綻はしない。

## ハイスコア

NVS (`nvs_flash`、名前空間 `devoursphere`、キー `highscore`)。レコードの中身は
`core/include/devoursphere/sim/high_score_record.hpp`、いつ書くかは
`high_score_store.hpp` (ハンドヘルドと共有)。

RP2 のような生フラッシュ書き込みではないので、もう一方のコアを止めることも
効果音からフラッシュを奪うこともない。それでも「1 回のプレイにつき 1 回、
DEAD で死亡音が終わってから」の方針はそのまま使う (それ以上の頻度で書く理由が無い)。

## 実機での性能

2026-09-20 に実機で確認した (ILI9881C の個体。`M5Tab5 ST touch FW version read failed` の
警告が出るが動作には影響しない)。

```
I (1386) devoursphere: internal free: 246231
I (1387) devoursphere: psram free: 31707040
I (1403) devoursphere: sound pack rate: 24000
I (1403) devoursphere: sound pack sounds: 16
I (1404) devoursphere: band buffer bytes: 51200      # 40 行のとき。現在は 45 行 = 57600
I (1422) devoursphere: panel write us: 17887
I (1472) devoursphere: internal free after setup: 134783
```

- **フレームレートは 40〜50fps**。SPHERE 1 を通してプレイしてハングなし。タッチも正常。
  その後 45 行の帯でもしばらく遊んで問題なし。
- **パネルへの書き込みは 1 フレーム 17.9ms** (`measureTransfer()`、他に何も走っていない状態)。
  1,843,200 バイトを 17.9ms なので **約 103MB/s**。

### 予想が外れたところ

設計時は LcdTap の実測 (GDMA の async memcpy / `pushImage()` でフレーム 1 枚に約 48ms) から
「パネルへの書き込みが壁になり 20fps 前後」と見積もっていたが、**PPA は 2.7 倍速い**。
PPA は専用の 2D-DMA を持ち、回転と拡大を通しながらブロック単位で書くので、
汎用 DMA の逐次 memcpy とは経路が違う。結果として:

- 17.9ms は約 56fps に相当し、**パネルの書き込みだけではまだ壁になっていない**
- 実測の 40〜50fps (20〜25ms) は CPU 側と PPA がほぼ拮抗して重なっている状態
- つまり 640x360 を選んだ判断はそのまま正しく、1280x720 にすれば CPU 側が
  4 倍近くに増えて一気に崩れる

PSRAM の帯域は DSI の走査 (ILI9881C: DPI 80MHz、940x1324 → 64.3Hz で約 118MB/s) と
PPA の書き込み (103MB/s を 40fps 分 = 約 74MB/s) が同居して回っていることになる。

### ShapoGFX 28d841f とアリーナ 32KB の後 (2026-09-24)

```
I (1390) devoursphere: internal free: 262135
I (1392) devoursphere: internal largest block: 172032
I (1409) devoursphere: band buffer bytes: 57600
I (1425) devoursphere: panel write us: 16066
I (1475) devoursphere: internal free after setup: 137887
```

- 起動直後の内蔵ヒープは 246,231 → **262,135** (+15.9KB、アリーナの 16KB 分)。確保後は 134,783 → 137,887 と
  +3.1KB に留まるが、これは帯が 40 → 45 行になって 12.8KB 増えたため (前回は 40 行で測った)。
- **最大の連続ブロックが 172,032**。60 行の帯 2 枚 (153,600) が 1 ブロックに収まる大きさで、
  かつて真っ暗になった `BAND_H` 60 が今は入る可能性がある (未確認)。
- パネル書き込み 17.9 → 16.1ms は PPA 側の値で、ShapoGFX とは関係しない (ばらつきと見ている)。

### 残っている確認事項

- **PPA が長時間の連続負荷で固まらないか。** ESP-IDF に未解決の報告がある
  ([#18999](https://github.com/espressif/esp-idf/issues/18999) 「continuous PPA load で
  `dma2d_connect` が無限に止まる」、[#19108](https://github.com/espressif/esp-idf/issues/19108))。
  SPHERE 1 を 1 回通した限りでは出ていないが、長時間・複数スフィアでは未確認。
  固まるようなら、フレームに 1 回の PPA 操作にするか CPU で回転させる。
- 2025-10-14 以降の個体 (ST7123) では未確認。M5GFX が自動判別して
  `M5Tab5 detected ST7123 display` を出す。
- `BAND_H` 45 と 40 でフレームレートに差が出るかは測っていない (60 は入らない。上記)。

計測オーバーレイはタイトル / ポーズ画面でディスクの上を倒すと出る
(off → フレームレートのみ → 全部)。Xiamocon / PicoSystem 版と同じパネル。
`CMD` はこのボードでは常に 0 (フレームバッファなので帯ごとのコマンドが無い)。

## 既知の課題 / やっていないこと

- ティアリングあり (`num_fbs = 1`)。ダブルバッファにするなら PSRAM を
  もう 1.84MB 使い、フリップを自前で管理することになる。
- バイリニア拡大のにじみ。ホストで再現した限り許容範囲だが、実機で見て
  気になるようなら最近傍で拡大する手段は PPA には無い (CPU でやることになる)。
- 電源ボタン / スリープ、バッテリー残量の表示。
- IMU、カメラ、マイク、Wi-Fi は使っていない (`M5.config()` で切ってある)。

## ベンチマーク

タイトル画面で **B の円を 3 秒** 押し続けると始まる (core/SPEC.md「ベンチマーク」)。約 33 秒
(60Hz で 1,980 フレーム、描ける速さで回す)。結果は画面中央と、シリアル (`printf`、`./monitor.sh`) に同じ行が出る。
A で次のページ、B で閉じる。`CMD` はこのボードでは 0、`DMA` は PPA の完了待ち、`W` は core0 が sim タスクを
待った時間。タッチパッドは結果の画面にも重ねて描かれるが、文字は中央に寄せるので重ならない。
