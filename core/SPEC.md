# Devour Sphere (コアプログラム)

ここではシューティングゲーム「Devour Sphere」のコアプログラムについて説明する。

## コンセプト

プレイヤーはサイバー空間の中に生まれた「エンティティ」。
その空間ではプレイヤーと同じようなエンティティが球状の物体「スフィア」の
表面付近に集まって弱肉強食の生態系を形成している。
エンティティは大きさによらず他のすべての個体を攻撃できる。
攻撃を受けたエンティティは「体力」を奪われ、体力がゼロになると死ぬ。
死んだエンティティは自身を構成したいた「フラグメント」をばらまき、それが他のエンティティの餌となる。
餌を食べることでエンティティは大きく成長し、より大きな他の個体を攻撃可能になる。
プレイヤーは他のエンティティと戦ってフラグメントを集めてより巨大化し、
今いるスフィアで最も巨大なエンティティとなることを目指す。

このゲームは「slither.io」から着想を得ている。

## フラグメント

エンティティの構成要素。
フラグメントには大きさがある。大きさは 1、2、4、8、... と 2 のべき乗の値をとる。
画面上では大きさに比例して「青緑色の正方形の 1 つの頂点を長く引き延ばした盾のような形」として描かれる。

## エンティティ

フラグメントが集まって意思を持つようになった存在。
プレイヤーも他のエンティティと同じ存在であるが、その形状は個体によって異なる。
浮遊しているフラグメントに触れて取り込むことでその分巨大化する。
体力ゲージを持ち、生まれた時は満タンだが、攻撃を受けることで体力が減る。
体力は浮遊しているフラグメントに触れることで、その大きさに応じて回復する。
自分の体に取り込めないほど小さなフラグメント (白く描かれる) も、触れれば回復に使われて消える。
体力がゼロになるとエンティティは死に、フラグメントがバラバラになって浮遊する。
エンティティ同士が接触している間は、小さい方から大きい方へ少しずつ大きさが移り、
小さい方は大きさがゼロになると消滅する。プレイヤーも同じように敵を取り込める。

### コア

エンティティの意識を司り、フラグメントを一つの塊に繋ぎ止める中核。
エンティティが死ぬとコアは消滅する。
画面上では白いフラグメントとして描かれる。

### エンティティの描画

フラグメントの集まりとして描画する。

エンティティは X, Y の 2 次元のローカル座標系を持ち、その中でコアとフラグメントが配置される。
エンティティの進行方向を Y 軸、エンティティの右方向を X 軸とする。
コアは原点より前方よりに固定されており、尖った頂点を前方に向けている (戦闘機のコックピットのイメージ)。
コアのやや後方にフラグメントが横に広く寄り集まっている (戦闘機の翼のイメージ)。
コアの大きさはエンティティ自身の大きさ (フラグメントの大きさの合計) に比例し、位置も大きさに比例して前進する (翼に埋もれないように)。

フラグメントの配置は次のように決定する。

- 全てのフラグメントは X 軸の正の方向にだけ存在するが、個々のフラグメントの「分身」が Y 軸を境に反転した位置に存在する。
- コア、フラグメント、フラグメントの分身を含めた全体としてエンティティは左右対称の見た目になる。
- 体内のコアとフラグメントは、互いの距離の 2 乗に反比例して引力が働き、距離の 3 乗に反比例して斥力が働く。
- フラグメントの位置はリアルタイムで計算され、浮遊しているフラグメントが取り込まれて体内に入ることで有機的に形が変化していく。
- 描画するときは X 軸の位置をやや大きくとり、翼のように横長に広がって見えるようにする。

これにより、コアのやや後方に左右対称にフラグメントが寄り集まった、鳥や飛行機のような形状になる。

個々のフラグメントの向きは、エンティティのやや前方もしくはコアを中心としてフラグメントの尖った頂点をその反対方向に向けて放射状に配置する。
フラグメントの尖った頂点が後方に向かって開くように配置されるので、より翼っぽくなる。

### 大きなフラグメントの合成

体内で同じ大きさ同士のフラグメントが十分近くまで接近すると合体し、2 倍の大きさのフラグメントとなる。

### 他のエンティティへの攻撃

体力を少しずつ消費して他のエンティティを遠距離攻撃できる。
プレイヤーはゲーム開始時に武器を選ぶ。

- バルカン砲: 縦スクロールシューティングゲームのバルカン砲のような弾。威力が小さく弾速も遅いが連射が速く、接近戦に有利。遠くに行くほど広く広がる。
- レーザー: 細長い弾。当たる範囲は狭いが弾速が速く、威力が強い。
- ミサイル: 敵を追尾する弾。自動で近くの敵を追尾するが、威力は弱い。

弾はエンティティの大きさに応じて大きく強力になるが、弾速は変わらない。
自分の弾はオレンジで、敵の弾はピンクがかった赤で描かれる。

レベルの低いスフィアでは敵はバルカンをたまにしか撃たない。
レベルが上がるにつれてミサイル、レーザーを使う敵が現れ、撃つ頻度も上がり、
偏差射撃や群れでの追跡、回り込みといった行動が加わる (実装仕様の「スフィア」「AI」参照)。

## スフィア

エンティティが集まる仮想の星。
スフィア上には最大 512 個の浮遊フラグメントと 224 体のエンティティ、128 発の弾丸が存在できる (`MAX_*`。
既定値で、小さなターゲットはビルド時に変えられる。「縮小構成のためのビルド時定数」の節)。
上限は実測のピーク (エンティティ 201、浮遊フラグメント 336、弾丸 84。レベル 1〜7 × 3 シード、AI 操作、10 秒と 3 分) の 1.5 倍以上で、
エンティティを 201 より増やすのはリスポーン時の巻き返し用の敵だけ (最大 4 体。「アップグレードと予備コア」の節)。
配列が一杯のときは生成を見送るか最古のものを置き換えるだけなので、上限は生成の有無にしか影響しない
(浮遊フラグメントは `DEVOURSPHERE_FRAGMENT_KEEP_LARGEST=1` なら最古ではなく最小を置き換え、最小より小さいものは生成しない)。
エンティティはスフィアの地表から少し離れた空中を地面と平行に移動する。
それぞれのエンティティの位置と進行方向は 3 次元ベクトルで表される。
プレイヤーより大きな敵はピンク、それ以下の敵は水色、懸賞首 (スフィアで最大になったことのある敵) は黄色で描かれる。
スフィア自体はイコソスフィアのワイヤーフレームのように描かれる。
プレイヤーがスフィアに降り立った時点ではさまざまな大きさのエンティティが
スフィア上を回遊しており、プレイヤーはその中でかなり小さい方の存在。

プレイヤーがスフィアで最も大きな存在になり、懸賞首を全部倒すと
そのスフィアから飛び立ち、新たなスフィアを目指す。
プレイヤーの大きさは画面上では維持されるが、
ゲーム内部ではプレイヤーを小さな存在に戻すことで
より巨大なスフィアに進出したように見える。
(内部で数値が際限なく大きくなってオーバーフローすることを防ぐ意味もある)

## 操作

何も押さなくても前方へ巡航する。
左右キーで左右に旋回。
上キーを押している間体力を消費しながら高速で前進する (ダッシュ)。
下キーを押している間減速し、最終的に停止 (ブレーキ)。
ブレーキを押しながら旋回することでクイックターンができる。
A ボタンで攻撃。押したままで連射。
B ボタンで緊急回避: 0.3 秒のバレルロールで横に滑り、その間は敵の弾が当たらない。次に使えるまでロールの後 0.3 秒。

入力装置はプラットフォームごとに違うので、キーやボタンの割り当てもプラットフォーム側が決める
(PC では ↑↓←→ と WASD が方向キー、スペースバーと J / L が A ボタン、I / K と C V B N M が B ボタン)。
タイトル画面に出す操作の案内文は `Renderer::setControlHints()` でプラットフォームから渡す。
既定値は PC のキーボード向けで、既定のまま使えば WASM 版の表示になる。

## 画面配置

プレイヤーの後方上をカメラがついていく三人称視点。
プレイヤーが左右に旋回するとカメラはやや左右にロールする (プラットフォームによっては切れる。
「カメラ」を参照)。
自分の体力ゲージと、今いるスフィア内での自分の大きさの順位が画面隅に表示される。
ダッシュ時はカメラがプレイヤーの後方に近づき、ズームして視界が狭くなる。
ブレーキ時はカメラがやや引いて広角になり、遠くを見渡せる。

## デザイン

黒い背景にワイヤーフレームのスフィア、その上空を単色で原色のエンティティやフラグメントが浮遊するサイバネティックな見た目。

## 実装

実装は C++ を使う。
コアプログラムは特定のプラットフォームに依存しないが、組み込み機器で実行することを想定し、
例えば計算量の多い部分は固定小数点化するなどの工夫をする。
描画周りは ShapoGFX (submodule/shapo-gfx/) を使う想定。

include/devoursphere にはアプリケーション実装側へ公開するヘッダファイルが置かれる。
src/ にはコアプログラムの実装が置かれる。

## 実装仕様

ここから下は上記の設計を実装した際の取り決めをまとめたもの。
数値の既定値は core/include/devoursphere/sim/config.hpp にあり、そちらが正。

### 構成

コアプログラムは 2 つのライブラリに分かれる。

| ライブラリ | ディレクトリ | 依存 | 内容 |
|---|---|---|---|
| `devoursphere::sim` | include/devoursphere/sim, src/sim | なし | ルール、物理、AI。整数演算のみ |
| `devoursphere::render` | include/devoursphere/render, src/render | sim, ShapoGFX | 状態を Surface に描く |

`sim` は浮動小数点を一切使わない。同じシードと同じ入力列を与えれば
WASM、ネイティブ、RP2350 のどれでもビット単位で同じ状態になる (テストで検証している)。
`render` は一部 float を使う (エフェクト、オーバーレイ、カメラ) が、描画結果がプラットフォームで多少違っても構わない。

```

  sim/fixed.hpp           固定小数点、三角関数、整数平方根、ベクトル、乱数
  sim/config.hpp          定数 (スケール、上限、速度、武器、AI)
  sim/entities.hpp        Entity, Fragment, FloatingFragment, Bullet, Spark, Button
  sim/game.hpp            Game: 状態機械と tick()、Event / EffectKind / SoundKind

  render/renderer.hpp     Renderer: beginFrame() / renderBand() / endFrame()
                          setControlHints() / pollEffects() はプラットフォームから呼ぶ
```

### 数値表現

- **Q30**: int32 で 1.0 = 2^30。単位ベクトル、三角関数、比率に使う。
  積は int64 で計算して 30 ビット右シフトする。
- **brad**: uint16 の角度。65536 = 1 周。sin/cos は 1025 点の 1/4 周テーブルと線形補間。
  atan2 は多項式近似 (誤差 0.1 度未満)。
- **units**: int32 の長さ。`FU = 256 units` を「フラグメント単位」と呼び、大きさ 1 のフラグメントの幅に相当する。
- スフィア半径 `R = 2^17 units = 512 FU`。2 のべき乗なので
  「単位法線ベクトルの差 (Q30) を 13 ビット右シフトすると units の弦長」になり、
  近傍判定を除算なしで行える (`tangentialDist2()`)。
- 32 ビットの整数平方根は「初期値を上から与えたニュートン法」で、32 ビット除算だけを使う
  (どのターゲットもハードウェアで割れる。RP2040 は SIO の除算器)。
  64 ビットの整数平方根は 2 ビットずつ確定していく筆算で、除算を使わない。
  結果は floor(sqrt(v)) で、ニュートン法だった頃と完全に同じ値。
  64 ビット除算は組み込みではライブラリ呼び出しで、tick あたり 2,000 回近く呼ばれる
  (配置物理の力の計算と正規化) ので、以前は tick の除算コストの大半がここにあった。
- 正規化 (`normalizeQ30`) は最大成分を [2^29, 2^30) に揃え、長さの 2 乗の上位 32 ビットの
  32 ビット平方根と 32 ビット除算から逆平方根の初期値を作り、ニュートン法 2 回
  (32x32→64 の乗算だけ) で 2^60 / len を得て 3 成分に掛ける。64 ビットの除算も平方根も使わない。
  厳密値との差は最大 4 LSB (Q30) で、以前の「成分ごとに厳密な除算」より短いベクトルの精度は
  逆に上がっている (以前は長さ 1 のベクトルがそのまま Q30_ONE 倍されて長さ √2 になるなど、
  入力が小さいほど粗かった)。
- `fragmentHalfSize()` は 21 エントリの表 (`constexpr` で同じ式から生成)。
  tick あたり 4,000 回近く呼ばれ、64 ビット乗算だった。
- 配置物理の力 (`addForce`) は、距離の 2 乗が 32 ビットに収まるとき (成分が ±32768 未満。
  ローカル座標はコア半径の 15 倍までしか離れないので実質常に) 32 ビットの平方根を使う。
  同じ floor(sqrt) なので結果は同一。
- 乱数は xorshift32。スフィアごとのシードは `Game::sphereSeed()`。

### 時間と入力

- 既定は 60 tick/秒 (`TICK_RATE`)。`Game::tick(buttons)` を呼ぶごとに 1 tick 進む。
  時間に関わる定数は秒あたりの値から `TICK_RATE` で tick あたりに換算して定義してあり
  (`ticks30()`、`fuPerSec()`、`turnPerTick()`、緩和量のシフトは `RATE_SHIFT` で補正)、
  tick レートを変えても挙動が保たれる。ただし決定性のため、同じ入力列から同じ結果を得たい
  プラットフォーム同士は同じ値でなければならない。
  以下の「毎 tick」の値は 30Hz 換算で書いてある。
- 性能の足りないプラットフォームは `DEVOURSPHERE_TICK_RATE` マクロで 30Hz に落とせる
  (対応するのは 30 と 60 のみ。`static_assert` で縛ってある)。定数は元々 30Hz で
  調整されていたので、これは素性の良い設定。`TICK_RATE` はヘッダ内の constexpr なので、
  **全翻訳単位で同じ値でなければならない** (ライブラリだけ別の値でビルドすると ODR 違反)。
  9 シード x 3 武器 x 120 秒の比較で、命中率・餌の取得ペース・死亡率は 60Hz と同等
  (撃破数のみ +8%)。ctest は 60Hz と 30Hz の両方でスイートを回す。
  **テストのループを tick 数で固定しないこと** — レートを変えると経過する game 時間が
  変わってしまう。実時間で書くか `ticks30()` を使う。
- 入力は 6 ビット: LEFT, RIGHT, UP (ダッシュ), DOWN (ブレーキ), A (攻撃・決定)、PAUSE (下記)。
- 描画は tick と独立に何度呼んでもよい (状態を変えない)。
- sim は 60Hz で回し、描画は追いつける範囲で行う。1 フレームに複数 tick 進めるときは
  **tick ごとに `Renderer::pollEffects()` を呼ぶ**こと。エフェクトのイベント
  (`Game::effects()`) は tick ごとにクリアされるので、これを怠るとフレーム内の
  最後の tick 以外の爆発やデブリが出ない。`beginFrame()` も同じ回収を行い、
  どちらも回収済みの tick は読み飛ばす。効果音の要求 (`Game::sounds()`、下記) も同じく
  tick ごとにクリアされるので、tick ごとに読むこと。

### ポーズとミュート

- **ポーズ**: PLAYING / LAUNCH / ARRIVE 中に `Button::PAUSE` を押すと `paused()` になる。
  ポーズ中の tick は入力だけを見て即座に返り、`tickCount_`、`stateTimer_`、`sphereTicks_`、
  効果音の最短間隔、乱数のどれも進めない。そのため**ポーズを挟んだ実行は挟まない実行と同じ状態になる**
  (テストで状態ハッシュの一致を検査している)。ポーズ画面では PAUSE で再開、DOWN でミュート切り替え。
  A は何もしない (再開の直後に撃たないように)。メニューと DEAD では PAUSE は無視される。
  ポーズと再開で menu_select が鳴る。
- **ミュート**: `muted()`。タイトル画面とポーズ画面の DOWN で切り替わる (`setMuted()` で
  プラットフォームからも設定できる)。ミュート中は `sounds()` が 0 を返すので、
  どのプラットフォームも自動的に静かになる。解除したときに menu_select が 1 回鳴る。
  設定なので `reset()` (ゲームオーバーからの再開) では変わらない。永続化はプラットフォームの仕事
  (wasm は localStorage、ハンドヘルドは電源を切ると戻る)。
- **描画**: `beginFrame()` はポーズ中 dt を 0 にして、カメラの補間・デブリ・塵・スコアの
  ロールアップを止める。HUD は「PAUSED」と `ControlHints::pause` の操作ヒントを重ね、
  ミュート中はタイトルとポーズ画面に「SOUND OFF」を出す。`Renderer::hud()` で HUD のスナップショットを
  読めるので、別コアで sim を回すプラットフォームはそこから `state` / `paused` / `muted` を取る。

### 効果音

音声の再生の仕組み (同時発音数、波形の形式、出力デバイス) はプラットフォームごとに全く違うので、
波形データと再生の機構はプラットフォーム側が持ち、sim は「この音を鳴らして」を出すだけにする。

- `Game::sounds()` は最後の tick で要求された音のビットマスク (`SoundKind` の値がビット位置)。
  tick ごとにクリアされる。`events()` や `effects()` と同じく、プラットフォームは tick の直後に読む。
  描画には関わらないので render 層は触らない。
- 同じ tick に同じ種類が何度要求されても 1 ビットなので、同時に敵が複数死んでも音は 1 回。
- 種類ごとに最短間隔を持てる (`SOUND_MIN_GAP_TICKS`、config.hpp)。今はフラグメントの取得と
  自機の被弾が 0.1 s。撃破直後にばらまかれた破片を数 tick かけて次々に飲み込むし、接触による
  吸収では大きさが移る tick ごとに要求されるので、そのままだと連打になる。
  間隔のカウンタは sim の状態の一部だが、乱数や物理には触れないので
  決定性テストの状態ハッシュには影響しない。
- 波形の並び (core/tools/pack_se.py、docs/play/se.bin) は `SoundKind` の順と一致させる。
  サンプルレートは全プラットフォーム 24 kHz (ESP32S3 の PDM ハードウェアの都合。impl/xiamocon/SPEC.md)。
  種類を足すときは `SoundKind`、`SOUND_MIN_GAP_TICKS`、`SOUND_KINDS`、pack_se.py の `SOUNDS`、
  play.js の `SE_NAMES` をすべて揃える (`static_assert` で個数は縛ってある)。

### 位置と姿勢

エンティティ、弾、フラグメントはすべて「単位法線 n (Q30) と中心からの距離 r (units)」で位置を持つ。
エンティティと弾はさらに進行方向の単位接ベクトル t を持ち、右方向は `t x n`。
移動は `n' = normalize(n + t * speed / r)`、その後 t を n' に直交化する。
旋回は t を n の周りに回転する。

高度 (r - R) はすべてのエンティティと浮遊フラグメントで同じ `ALTITUDE` (12 FU)。
出現時などにずれた場合は毎 tick 目標値に 1/32 ずつ近づく。

フラグメントの見た目の大きさ (凧の半径) は大きさの 4 乗根に比例する:

```
halfSize(k) = (FU / 2) * 2^(k/4)      (大きさ 2^k のフラグメントの凧の半径)
```

大きさが 2 倍になっても幅は 19% しか増えないので、合体で大きさが倍々に増えても
画面上の巨大化はゆっくり進む。コアの大きさ、体の半径、弾速、カメラ距離もこの値から決まる。

### エンティティ

- `size` はフラグメントの大きさの合計で、これが正。フラグメントの一覧はその視覚的な分解であり、
  フラグメント数の上限 (8) に達したときは最小の 2 個を強制合体させるため合計は size と一致しないことがある。
- 体力 `hpMax = 32 * size`。フラグメントを取り込むと hpMax が増え、hp は比率を保つ。
  体力が減るのは敵の攻撃を受けたときだけ (ダッシュも発射も消費しない)。自然回復はなく、
  フラグメントに触れたときにその大きさに比例して `32 * 3 * フラグメントの大きさ` 回復する
  (体の 1/32 のフラグメントで約 9%)。敵を吸収したときは移ってきた大きさの分に加えて、
  相手から吸い取った体力の分だけ回復する (捕食と吸収を参照)。
  見た目のフラグメントの再構成 (縮んだときの分割やクリティカルの補充) では回復しない。
  敵の弾がプレイヤーに与えるダメージは、撃った側が自機の `hitSizeRatioMax` 倍 (AI ティア表: レベル 1〜4 で
  2 倍、5〜7 で 3 倍、8 以降 4 倍) の大きさだったものとして頭打ちにし (巨大な敵の弾も「数倍の敵の弾」の
  痛さ)、さらに 1 発で hpMax の 25% まで (`PLAYER_MAX_HIT_PERCENT`)。この上限は難易度の倍率と Shield の
  軽減をすべて適用した後、体力から減算する直前にかける (Shield で上限以下まで減ったダメージはそのまま
  受ける)。被弾後 0.1 秒 (`PLAYER_MERCY_TICKS`) は敵の弾が当たらない (複数の敵に同時に撃たれても一瞬で
  溶けない)。
- 巡航速度 `SPEED_BASE + SPEED_PER_LOG2 * log2(size)` (大きさ 1 で 15 FU/s、倍ごとに 2.5 FU/s 増)。ダッシュは最大 2.25 倍
  (体力は消費しない) で、`dashLevel` (0..256) が 2 秒かけて上がり、解除後 1 秒かけて下がる。
  速度はこの値に比例して増減し、カメラのズームと塵のエフェクトもこの値に追従する。
  旋回速度はダッシュが半分以上のときに落ちる。ブレーキは速度を 0 に向けて減衰させ、旋回速度が 2 倍になる。
- 緊急回避 (B ボタン、自機のみ): `DODGE_TICKS` (0.3 秒) の間、平均で巡航速度の 4 倍 (`DODGE_SPEED_MUL`) で横に
  滑りながら進行方向まわりに 1 回転する。横滑りの量と `bank` はどちらも経過時間のスムーズステップ
  (3t² − 2t³、`dodgeProgressQ16()`) から決めるので、始まりと終わりが滑らか (速度 0 から立ち上がり、0 に戻る)。横方向は旋回入力の側、入力が
  なければ 60 FU 以内の最寄りの敵弾から遠ざかる側、それもなければ右。回避中は敵の弾が当たらない
  (吸収は防がない)。次の回避まで `DODGE_COOLDOWN_TICKS` (押した tick から 0.6 秒 = ロール 0.3 秒 + 0.3 秒。
  1.x は 3 秒だったが、強敵とのドッグファイトで役に立たないので 2.0 で縮めた)。押した tick から数えて `DODGE_TICKS` tick が
  無敵。状態は Entity ではなく Game が持つ (`dodgeTicks_` / `dodgeCooldown_` / `dodgeDir_`、ハッシュに含む)。
  開始時に `Event::PLAYER_DODGED` を立てる。
- 旋回は最大 90 度/秒 (ブレーキ中 180 度、ダッシュ中 60 度)。旋回入力は `turnLevel` (-256..256) に
  0.3 秒かけて立ち上がり、離すと同じ時間で止まる。旋回角速度と `bank` (進行方向まわりのロール、
  最大 28 度、ブレーキ中 40 度、毎 tick 1/8 ずつ追従) はこの値に比例する。描画側のカメラのロールも同じ値から決まる。

フラグメントの配置 (ローカル座標、units):

- コアは `(0, coreY)` に固定。`coreHalf = halfSize(log2 size) * 5/8`、`coreY = coreHalf * 3/2`。
- フラグメントは `x >= halfSize/4` の右半平面に置き、`(-x, y)` に分身があるものとして力を計算する。
- 力は「平衡距離 d0 = (半径の和) * 9/8」を境に、`F = A * (d0/d)^2 * (1 - d0/d)` で
  遠くでは 1/d^2 の引力、近くでは 1/d^3 の斥力になる (A = 半径/16、-4A..A にクランプ、
  遠方では最低 A/8 の引力)。相手はコア、他のフラグメント、全フラグメントの分身 (自分の分身を含む)。
- さらにローカル座標の原点への弱いばね (距離/32) で、置き去りにされたフラグメントも体内に戻る。
  速度の上限は `半径/4 + 原点からの距離/16` で、遠いフラグメントほど速く戻る。
- 速度は毎 tick 1/4 に減衰し (強い減衰で揺れが残らない)、力の強さ A は半径/16、
  速度の大きさは半径/8 (+ 原点からの距離/16) に制限する。半径/64 以下の速度は 0 にして静止させる。
- 同じ大きさのフラグメントが半径の 5/8 より近づくと合体する (1 tick に 1 組)。
  体内のフラグメント数が上限 (8) の半分を超えているときは半径の 2.5 倍まで合体し、
  それでも合体する組がなければ最も近い同じ大きさの組を合体させる (体が混み合わないように)。
- プレイヤーから 90 FU 以内の個体は毎 tick、それより遠い個体は 4 tick に 1 回更新する。
- `bodyRadius` はフラグメントの広がりから求め、捕食や被弾の判定半径に使う。

描画側はフラグメントの位置を x 方向に 1.4 倍して翼のように広げ、
尖った頂点を「コアのやや前方の焦点 (`layoutFocusY`)」から遠ざかる方向に向ける。

### 武器

| 武器 | 弾速 (FU/s、大きさ 4 の個体) | 寿命 (秒) | 間隔 (秒) | 威力 (× size / 8) | 同サイズを倒す弾数 | 拡散 | 誘導 |
|---|---|---|---|---|---|---|---|
| バルカン | 75 | 1.5 | 0.13 | 5 | 52 | ±5 度 | なし |
| レーザー | 240 | 0.93 | 0.47 | 20 | 13 | なし | なし |
| ミサイル | 52 | 3.3 | 0.4 | 10 | 26 | ±20 度 | 120 度/秒 |

- 弾速は持ち主の見た目の大きさ (フラグメントの凧の半径、つまり sqrt(size)) に比例する。表の値は
  大きさ 4 の個体のもので、大きさ 16 なら 2 倍、64 なら 4 倍になる。射程 (弾速 × 寿命) も同様に伸びる。
- クリティカルヒット (最大の敵には起きない、下記): 命中の 1/30 は体力を減らす代わりに、体の約 1/10 (以下の最大の 2 のべき乗) の
  フラグメントを撃った側と反対側へ 90 FU/s で弾き出す (`criticalHit()`)。`size` を減らして
  `syncFragments()` で見た目を追従させるので、該当する大きさの独立したフラグメントがなければ
  大きなフラグメントが分割される。弾き出されたフラグメントは元の持ち主が 3 秒間取り込めず、
  自機の吸い寄せも効かない (`FloatingFragment::owner` / `ownerGuard`)。
- 弾は持ち主以外のすべてのエンティティに当たる (高度は問わない)。判定は「この tick に飛んだ線分」と
  相手の中心との接線方向の距離 < `bodyRadius + 弾半径` (掃引判定。速い弾が小さな相手を飛び越えない)。

### 捕食と吸収

- 浮遊フラグメントは `bodyRadius + フラグメント半径` 以内で触れると取り込む。ただし自分の 1/32 未満
  (`FOOD_NOTICE_RATIO`) のフラグメントは体に加わらず、その大きさに応じた回復だけをして消える。
  AI はそうしたフラグメントを追わない。
- どちらが取り込むかは「実効的な大きさ」`size × (0.25 + 0.75 × hp / hpMax)` (`effectiveSizeQ8()`) で決める。
  大きな相手でも遠距離攻撃で弱らせれば取り込める: 1.5 倍の相手は体力 5/9 未満、2 倍は 1/3 未満、3 倍は
  1/9 未満で自分より実効的に小さくなる (「撃って弱らせて体当たり」が格上に勝つ筋)。対称なので体力 1/3 の
  自機は半分の大きさの敵に食われ得る。機体の色 (ピンク / 水色) もこの値で分ける。
- エンティティ同士の体が重なっている間 (3D 距離 < bodyRadius の和の 1/2)、毎 tick
  実効的に小さい方の `size >> 7` (最低でも 4 tick に 1) が大きい方へ移る。大きさが 0 になった方は消滅する。
  体力も移る: 10 tick ごと (毎秒 6 回、吸収エフェクトの脈動と同じ周期) に小さい方の hpMax の 5%
  (`ABSORB_HP_PCT`) を小さい方から差し引き、同じ量だけ大きい方が回復する (体格差が大きいほど、
  大きい方にとっては僅かな回復になる)。体力が 0 になった方はその場で撃墜と同じように砕けて
  フラグメントを撒く (吸った側が自機なら捕食のスコア)。
  `size` が正なので、見た目のフラグメントは `syncFragments()` で追従させる
  (減った側は最小のフラグメントから消え、増えた側は接触点に新しいフラグメントが現れる)。
  プレイヤーも同じ規則で敵を取り込む。
- フラグメントやエンティティを取り込んだ直後の 1 秒間は吸収されない (`absorbGuard`)。
  成長して新たに交戦可能になった隣の個体に即座に吸収されるのを防ぐ。
  出現直後の無敵時間 (`invincible`) は被弾と吸収の両方を防ぐ。
- 自機の `bodyRadius + 32 FU` 以内にある浮遊フラグメントは自機へ加速し、吸い寄せられる。
  加速度は大きさ 4 の自機で 128 FU/s² で、自機の見た目の大きさ (`attractScaleQ8()`。
  フラグメントの凧の半径、つまり size の 4 乗根。4 レベルごとに 2 倍) に比例して強くなる
  (上限 16 倍)。巨大化すると自機自身が速く、捕捉半径も広くなるため、固定の加速度では
  吸い寄せが追いつかなくなる。速度の上限は 480 FU/s、ただし自機の `bodyRadius` が
  それを超える大きさになったら `bodyRadius`/tick まで緩和する (それ以上だと 1 tick で
  体を飛び越えて捕捉されないことがある)。
- 死んだエンティティはフラグメント (と分身) を浮遊フラグメントとしてばらまく。
  初速は `0.25～0.5 FU/tick × (8 + log2 size) / 8` で外向きに飛び散り、毎 tick 1/32 ずつ減速する。
  ただし**自機の残骸は何も残さない**。3 秒の `ownerGuard` と離れた地点へのリスポーンのせいで
  自機自身には絶対戻らず、自機を倒した敵の餌にしかならないため。時間切れの自壊も同じ経路だが、
  直後にスフィアを作り直すので観測できる差はない。

### スフィア

- エンティティ 200 体で開始し、減ると 0.5 秒ごとに小さな個体が補充される。
  大きさの指数は `min(2 回の一様乱数)` で小さい個体ほど多い。上限は `8 + レベル` (最大 16)。
  最初の 3 体は上限の大きさで生成する。
- 「餌」として浮遊フラグメント (大きさ 1～8) を 320 個ばらまき、400 個を下回る間は毎秒 7.5 個補充する。
- レベルによる敵の振る舞いは AI ティア表 `AI_TIERS` (レベル 1〜10、以降は 10 と同じ) で決まる。
  難易度はスフィアのレベルで進み、自機のアップグレードには (わずかな倍率を除いて) 依存しない。

  | レベル | 発射確率 | 武器 (ミサイル / レーザーの割合、残りはバルカン) | 弾の頭打ち | 度胸 (60 FU / 40 FU) | 追加される行動 |
  |---|---|---|---|---|---|
  | 1 | 19% | 0 / 0 | 2 倍 | 1.5 / 1.1 倍 | 徘徊・餌・獲物。回避なし。2 倍までの敵が自機を狙う |
  | 2 | 38% | 0 / 0 | 2 倍 | 1.5 / 1.1 | 離脱 3 発、反撃 25% |
  | 3 | 55% | 25% / 10% | 2 倍 | 2 / 1.25 | ダッシュ、偏差射撃、離脱 2 発、反撃 50%、3 倍までの敵が自機を狙う |
  | 4 | 70% | 33% / 20% | 3 倍 | 2 / 1.25 | 群れ、反撃 60%、4 倍までの敵が自機を狙う |
  | 5 | 86% | 33% / 33% | 3 倍 | 2.5 / 1.5 | 回り込み、反撃 75% |
  | 6 | 100% | 33% / 40% | 3 倍 | 2.5 / 1.5 | 離脱 1 発、反撃 85%、6 倍までの敵が自機を狙う |
  | 7 | 100% | 33% / 45% | 4 倍 | 3 / 1.75 | 反撃 100% |
  | 8 | 100% | 30% / 50% | 4 倍 | 3 / 2 | 8 倍までの敵が自機を狙う |
  | 9 | 100% | 25% / 50% | 4 倍 | 3.5 / 2 | |
  | 10 以降 | 100% | 25% / 50% | 4 倍 | 4 / 2.5 | 優先度 ÷2.2 |

  2026-09-19 の 3 回目の調整: 2 回目でも作者には易しかったので、度胸と反撃を全レベルで前倒し・強化し
  (反撃は自分の 2 倍までの射手に、体力 1/4 より多ければ)、群れの呼び掛け距離を 90 FU にした。

  発射確率は 0.27 秒ごとの判断で、獲物を前方 15 度・射程内に捉えたときに撃つ確率 (256 分率 `fireChance`)。
  補充される敵の武器も同じ表から引く。各行動の意味は「AI」を参照。
- 制限時間: スフィア 1 は 6 分、スフィア 2 は 5 分、スフィア 3 以降は 4 分 (`sphereTimeLimitTicks(level)`、
  `Game::sphereTimeLimit()`。1.0 では一律 5 分だったが、ほとんどのプレイが 3 分以内に終わるので 2.0 で
  一律 4 分に縮め、初心者が操作を覚える最初の 2 スフィアだけ 3.1 で延ばした)。時計 (`sphereTicks_`) は PLAYING 中で自機が
  生きている間だけ進む (撃墜されてリスポーンを待つ間、飛行演出、ポーズでは止まる)。残り 30 秒
  (`TIME_ALARM_TICKS`) からは 1 秒ごとに `SoundKind::TIME_ALARM` を要求する。0 になると自機は撃墜と同じように
  音を立てて砕け (`killEntity`、`Event::SPHERE_TIME_UP`、`timeUp()`)、残骸を 3 秒見届けた後、予備コアがあれば
  `restartSphereAfterTimeUp()`: 予備コア −1、全アップグレード −1、同じレベルのスフィアを作り直し、
  最初のスフィアと同じ ARRIVE (カメラが自機の前方にある状態から、切り替え無し) で入り直す。自機は着地時の
  大きさ (レベル 1 なら 4、それ以外は 8) に戻り、表示用の縮尺はそのままなので小さく見える。予備コアが
  なければ DEAD。長時間同じスフィアに居座って自機や敵が際限なく巨大化することを防ぐのが目的。
- 順位は体力を考慮しない純粋な `size` の大小 (`updateRanks()`)。最大の敵は `largestEnemy()` (自機を除く
  最大の個体)。1.x では最大の敵にはクリティカルヒットが出なかった (撃っているうちに縮んで順位が
  入れ替わるのを防ぐため) が、2 位の自機と体格差がありすぎると勝ち目が無くなるので 2.0 で取り消し、
  ほかの敵と同じくフラグメントを落とす。
- 懸賞首 (`Entity::bounty`、2.0): 敵が総合 1 位 (自機より大きく、敵の中で最大) になった瞬間にフラグが立ち、
  死ぬまで消えない。上位 3 位 (自機を含む全個体の中で。同じ大きさは圏内扱い) から外れると下ろすが、
  **生きている最後の懸賞首は圏外に落ちても下ろさない**。撃たれて縮んだ首が圏外に落ちた瞬間にクリアに
  なる (交戦中の肩透かし) のを防ぐためで、そのとき相手は自機よりずっと小さいので食べに行けば終わる。
  自機が 1 位でない間は必ず誰かが懸賞首なので、`bountyCount()` が 0 なら自機が 1 位で、
  かつて 1 位だった敵は全部死んでいる。自機が 2 位の間に敵同士で 1 位が入れ替わると懸賞首が複数になり、
  全員倒す必要がある (上位 3 位の規則で数は抑えられる)。判定は `updateRanks()` の 1 回の走査
  (順位、最大の敵、上位 3 個の大きさ、生きている懸賞首の数) と、懸賞首が 2 体以上のときだけ走る
  2 回目の走査で、tick あたりの追加コストはエンティティ 1 体につき比較 3 回程度。プレイヤーは懸賞首に
  ならない。
- 懸賞首が 0 のまま 4 秒 (`CLEAR_GRACE_TICKS`、`clearGrace_`。撃破の音と破片を見届ける時間) 経つと
  LAUNCH 状態 (5 秒間) になり、次のスフィアへの
  飛行 (ARRIVE 状態、5 秒間) を経て次のスフィアに降り立つ。飛行中 (LAUNCH と ARRIVE) は
  自機は被弾・捕食・吸収 (する側もされる側も) の対象外になり (`playerFrozen()`)、敵の AI も
  自機を見ない (はるか上空にいる) ので、翼の形も体力も変わらない。LAUNCH 中は順位表示を固定する。
  無敵時間は着地した瞬間に 2 秒始まる (飛行中は frozen で守られているので、点滅させない)。

  飛行の軌道 (`moveEntity()` の高度、いずれも巡航高度 `ALTITUDE` からの高さ):
  - LAUNCH: `LAUNCH_ALTITUDE` (900 FU) を目標に `t²` で加速しながら上昇し、ARRIVE の切り替えまで
    同じ式で上昇を続ける (LAUNCH の終わりで約 870 FU、切り替え時に約 1050 FU)。
  - ARRIVE の `ARRIVE_SWITCH_TICKS` (1 秒) の tick で**スフィアを切り替える** (`switchSphere()`):
    レベル +1、自機のフラグメントの指数を `log2(size) - 3` だけ下げて内部的に小さく戻し
    (下げた分を `playerDisplayScaleLog2()` に積算、HUD の表示用)、`startSphere(true)` で
    新しいスフィアを作る。900 FU から離れた前のスフィアより 500 FU から近づく次の
    スフィアの方が大きく見える (自機は縮んでいるので、自機比では同じくらいの高さ)。
  - **自機は直進したまま、次のスフィアが前方に現れる。** 切り替えの瞬間に速度ベクトルが
    「上昇」から「降下」へ折れると、横から見て機体が急に頭を下げる。そこで自機の frame を
    右軸 (t × n) まわりに回して、新しい frame での降下 (t 方向に speed、n 方向に降下勾配 slope)
    が切り替え前の速度ベクトル (t·speed + n·climb) と同じ世界方向になるようにする:
    `vOld` を前の速度の単位ベクトル、`w` を vOld を n 側へ 90 度回したもの、
    `(c, s) = (speed, -slope) / |(speed, slope)|` として `n' = vOld·s + w·c`、`t' = vOld·c - w·s`。
    星空は世界に固定なので飛ばず、旧スフィアは後方、新スフィアは前方 (n' のほぼ逆) に来る。
    切り替え後の速度は縮小後の巡航速度と降下の初期勾配で、`playerClimb_` にもその勾配を
    入れておく (描画側が同じ tick に同じピッチを出せるように)。
  - 切り替え後: `(残り時間)²` で減速しながら降下し (`descentTarget()`)、状態の終わり 1 秒前に
    巡航高度に達する (残りの 1 秒で機体が水平に戻ってからプレイヤーに操作が渡る)。
    高度の追従は 1/8 per tick の一次遅れなので、切り替え時の r には定常の先行分
    (勾配 × 8) を足しておき、最初の tick から勾配どおりに降りる。
  - 自機は飛行中ダッシュ扱い (`dashing`) で接線方向にも進む。ARRIVE の最後の 1 秒
    (`DASH_RAMP_DOWN_TICKS`) はダッシュをやめ、`dashLevel` が 0 に戻ってから着地する。
    そうしないと PLAYING に入った瞬間にカメラがダッシュの位置へ飛び、1 秒かけて戻る。
  - ロール: LAUNCH では 0.5 秒後から、ARRIVE では 1.5 秒後から 3 秒かけて進行方向まわりに
    1 回転する (`bank` を状態タイマーから直接決めるので、終わりでちょうど 0 に戻る)。
    その間は旋回による bank の追従を止める。
  - 半径方向の 1 tick の移動量を `playerClimb()` で公開する。描画側はこれと `speed` から
    飛行経路の仰角 (ピッチ) を作る。sim のフレームにはピッチが無い。
  - 最初のスフィアも同じ ARRIVE を最初から飛ぶ (`beginArrival()`) が、離れるスフィアが
    無いので切り替えは起きない (`switchPending_`、LAUNCH から入ったときだけ真。ハッシュに含む)。
    降下の式を 1 秒ぶん遡った高さ (約 890 FU) から最初から降下する。途中で頭を下げることはない。

### アップグレードと残機 (Upgrade / Cores)

名称: アイテム = **Upgrade**、シールド = **Shield**、パワーアップ = **Overdrive**、スピードアップ = **Thruster**、
残機アップ = **Extra Core**、残機 = **Cores** (予備のコア)。

- 最初のスフィアはアップグレードなし、予備コア 1 で始める。Shield / Overdrive / Thruster はレベル 0～3、
  予備コアは最大 3。レベル上限 (または予備コア上限) で余分に取ると 500 × 倍率 × 滞在係数のボーナススコア。
- スフィア開始時に Shield / Overdrive / Thruster を 1 個ずつ、1/3 の確率で Extra Core を、
  それぞれ別の敵に持たせる (`Entity::upgrade`)。持ち主のフラグメントは白い
  ワイヤーフレームで縁取られ、近くでよく見ると分かる。持ち主が死ぬ (撃墜・吸収) と
  浮遊アップグレード (`floatingUpgrades`、最大 8 個) として放出され、ゆっくり漂って期限なく残る。
  敵は取れず、自機の吸い寄せも効かない。自機が `bodyRadius + 2 FU` 以内に触れると取る。
- Shield: 被弾ダメージを 100 / 75 / 50 / 50 % に (クリティカルヒットのフラグメント放出には効かない)。
  Lv.3 は毎秒 hpMax の 5% 自動回復 (`SHIELD_REGEN_PCT_PER_SEC`。10% では強すぎた)。
- Overdrive: 連射速度を Lv.1 で 25% アップ、Lv.2 で 50% アップ、Lv.3 で 2 倍
  (発射間隔 100 / 80 / 67 / 50 %)。
- Thruster: ダッシュの速度増分を Lv.1 で 25% アップ、Lv.2 で 50% アップ、Lv.3 で 2 倍
  (100 / 125 / 150 / 200 %)。
- Extra Core: 予備コア +1。

死亡時に予備コアがあれば、砕け散った自機の位置を 3 秒間 (`RESPAWN_DELAY_TICKS`) 幽霊として
巡航させてカメラで見届けた後、1 つ消費し、全アップグレードのレベル −1、大きさ 3/4
(`RESPAWN_SIZE_KEEP_PCT`。半分だと Sphere 5〜6 以降で復帰直後に瞬殺されるため。最低 4) で
リスポーンする (`respawnPlayer()`)。位置はランダムな候補 24 点から最寄りの敵が最も遠い点。
ただし距離を測る相手は**自機の 50% 以上の大きさの敵だけ** (`RESPAWN_THREAT_PCT`)。小さい敵は
巻き返しを潰す相手ではなく、それも避けようとすると本当に危険な敵から離れる距離を損するため。
無敵 2 秒。スコアは維持。予備コアがなければ DEAD。
失ったレベルの分のアップグレードは、リスポーン地点を中心とする半径 110 FU (`UPGRADE_SCATTER_FU`、
地平線までの約 111 FU とほぼ同じ。近すぎると取り戻すのが簡単すぎるため) の円上のランダムな点に浮遊アップグレード
として置く (`scatterLostUpgrades()`。時間切れのやり直しでも着地点の周りに置く)。スフィアが進んでから
弱った状態で復帰したときに取り戻す機会を与える。ただし同じ種類はスフィア上に (敵が持っている分も含めて)
最大 2 個 (`UPGRADE_KIND_MAX_ON_SPHERE`、`countUpgradeKind()`) までしか生成しない。

さらに、リスポーン地点の周囲に**巻き返し用の敵**を置く (`spawnRespawnPack()`)。Sphere 5〜6 以降では
2 分ほどで自機がスフィア全体を追い越してしまい (補充される敵は `4 + sphereLevel` で頭打ち。「スフィア」
の節)、周囲には生き残った巨人と、食べても足しにならない雑魚しか残らない。3/4 の大きさで復帰しても
成長し直す手段が盤面に無い状態になるため、その分を置いてやる。

- 量: **ランクが 1 つ上の敵 (自機より大きい中で最小の個体) との大きさの差**。ただし
  **死亡で失った大きさの 1.5 倍** (`RESPAWN_PACK_MASS_NUM` / `_DEN`) を超えない。死ぬことが
  成長手段になってはいけないため。この上限は失った分 (元の 25%) の 1.5 倍 = 復帰後の大きさの
  ちょうど半分なので、実際には常に 1 体になる (分割は上限を上げたときのための一般形)。
- 分割: 1 体が自機の 90% (`RESPAWN_PACK_CHUNK_PCT`) を超えるなら複数体に割る。最大 4 体
  (`RESPAWN_PACK_MAX`)。90% を超える敵は、体力が減った自機を吸収できてしまい救済にならない。
- 量が自機の 12% (`RESPAWN_PACK_MIN_PCT`) に満たないなら何も置かない。ランクが 1 つ上の敵が
  すぐ上にいる = 自力で巻き返せる状態なので救済は要らない。自機が 1 位のときも置かない。
- 位置: リスポーン地点を中心とする半径 70 FU (`RESPAWN_PACK_FU`) の円上のランダムな点。
- それ以外は普通の敵 (AI ティアの武器、1 秒の無敵) だが、`Entity::noScore` が立っていて
  倒しても 0 点 (「スコア」の節)。懸賞首は自機より大きい個体にしか付かないので突破条件には影響しない。

難易度: 敵の強さはスフィアのレベル N で進む (スフィアの AI ティア表を参照)。アップグレードは報酬であって
罰ではないので、自機のアップグレード合計レベル L (0～9) の影響はわずかにとどめる: 敵の発射確率を
(100 + 5 L) %、敵の弾が自機に与えるダメージを (100 + 5 L) % にする。ダメージにはさらにスフィアの
(100 + 15 (N - 1)) % (上限 250%、N=11 以降) が掛かる (レベル 4 で 145%、レベル 10 で 235%) (`DIFF_*`)。
この倍率は敵の弾が自機に当たったときだけにかかり、自機の弾や敵同士の撃ち合いには影響しない。
体格比の頭打ち、Shield の軽減、1 発 25% の上限はこの後にかかる (エンティティの節を参照)。

同サイズのバルカン敵 1 体に全弾当てられたときの全快からの生存秒数 (`sim_bench ttk` の出力、Shield なし):
レベル 1 で 37 秒、3 で 9.5 秒、5 で 4.6 秒、7 で 3.6 秒、10 で 3 秒。相手が 2 倍以上なら半分以下。
2026-09-19 の最初の調整 (レベル 7 以降 5 秒、頭打ち 2 倍固定、上限 170%) は作者が Sphere 10 に
到達してしまったので、到達レベルが半分〜2/3 になるように締めた。

### スコア

すべての得点は `基礎点 × 1.1^(レベル-1)` (`SCORE_LEVEL_GROWTH_PCT`、`levelMultQ8()` が Q8 で整数の
反復乗算で求める: 256, 281, 309, 339, ...) で、内部では Q8 (1 点 = 256) の 64 ビット整数に飽和加算する
(`Game::score()` は整数部)。以前の「スフィアごとに 2 倍」と滞在係数はスコアのインフレが激しすぎたので廃止した。

| 行為 | 基礎点 |
|---|---|
| プレイヤーの弾で敵を撃破 | `100 × (相手の大きさ ÷ 自分の大きさ)²` (比率は 0.25～3 にクランプ) |
| 接触で敵を消滅させた | 30 |
| フラグメントが体に加わった | 1 |
| スフィア突破 | `2000 + 4000 × ボーナス対象時間 ÷ 4 分` (`SCORE_CLEAR_BASE` / `SCORE_CLEAR_TIME_BONUS`) |

リスポーン時に置かれる救済用の敵 (`Entity::noScore`、下記) だけは撃破も接触消滅も 0 点。
そうしないと、わざと死んでリスポーンした方が稼げることになってしまう。散ったフラグメントの
回収点 (1 点) は残るが、撃破点 (6〜900 点) に対して無視できる。

ボーナス対象時間は「残り時間 − 猶予」を 0 でクリップした値 (`sphereBonusGraceTicks(level)`: スフィア 1 は
2 分、スフィア 2 は 1 分、スフィア 3 以降は 0)。最初の 2 スフィアに与えた延長分は得点にはしない、という
意味で、どのスフィアでもボーナスの幅は同じ 4 分になる (`制限時間 − 猶予 = 4 分` を config.hpp の
`static_assert` で固定)。スフィア 1 で残り 2 分以下、スフィア 2 で残り 1 分以下の突破はボーナス 0 点。

突破ボーナスは即突破で 6,000、時間ぎりぎりで 2,000。4 分で同格を 25〜40 体倒すと基礎点 2,500〜4,000 に
なるので、短期決戦でボーナスを稼ぐ戦略と敵を倒し続ける戦略が同じ桁で釣り合う (中級者の実測は 1 スフィア
2〜2.5 分)。突破時にそのスフィアで得た点 (`sphereScore()`、スフィア開始時からの差分)、かかった時間
(`clearTicks()`)、ボーナス (`clearBonus()`) を覚えておき、LAUNCH の間 HUD に出す。
スコアはゲーム開始時に 0 に戻り、状態ハッシュに含まれる。ハイスコアと、そのときに到達していたスフィアは
プラットフォーム側 (WASM 版は localStorage) が保持し、表示のために `setHighScore(score, sphere)` で渡す。
スコアがプレイヤーのものかどうかは `Game` が判定する (`scoreIsPlayers()`): タイトルと武器選択では AI が
操作するデモも捕食や撃破で得点するが、それはハイスコアにならない。プラットフォームは毎フレーム (WASM 版は
毎秒) `keepHighScore()` を呼び、プレイ中のスコアがハイスコアを超えていればその場で取り込まれて true が返るので、
そのときだけ保存する。

### 状態機械

```
TITLE  --A-->  WEAPON_SELECT  --A-->  ARRIVE (切り替え無し)  -->  PLAYING  --懸賞首 0 が 4 秒-->  LAUNCH
                                                                 ^  |                       |
                                                                 |  +--死亡-->  DEAD  --A-->  TITLE
                                                                 |                (2 秒後)   (新しいシード)
                                                                 +--  ARRIVE (1 秒でスフィア切り替え、5 秒)  <--+
```

ARRIVE は enum の末尾 (DEAD の後) に足してあるので、WASM の `ds_get_state()` の既存の番号は変わらない。
時間切れは死亡と同じ流れで自機が砕け、3 秒見届けた後、予備コアがあれば ARRIVE (切り替え無し、同じレベルの
新しいスフィア) へ、なければ DEAD (スフィアの節を参照)。

WEAPON_SELECT では左右キーでも上下キーでも武器を選べる (画面が狭くて選択肢が縦並びに
なったときも、並びと操作が食い違わないようにするため)。A ボタンで決定。
TITLE と WEAPON_SELECT の間はプレイヤーを AI が操作し、アトラクトモードになる。
PLAYING で自機が死んだとき、予備コアがあればリスポーンして PLAYING のまま続く (上記)。
自機が死んでいる間 (リスポーン待ちと DEAD) は自機の位置を「方位を固定したまま巡航速度で前進する幽霊」
として動かし続け、カメラはそれを (通常よりやや後方から、ゆっくり追従して) 追う。リスポーン後は
引いた状態のカメラが新しい位置へ滑らかに寄っていく。

### AI

約 0.27 秒ごと (個体ごとにずらす) に判断する。レベルで変わる数値と行動の有無はスフィアの
AI ティア (`AI_TIERS`、`Game::aiTier()`。スフィアの節の表) から取る。

1. 脅威: 自分より実効的に大きい個体は、60 FU 以内で `fleeFarPct` を超えるか、40 FU 以内で `fleeNearPct` を
   超えるときだけ脅威として逃げる (「度胸」。値はスフィアの節の表: レベル 1 で 150 / 110 %、10 で 400 / 250 %。
   レベルが進むほど少し大きい相手からは逃げなくなる)。`AI_DASH` (レベル 3 以降) では近ければダッシュ。
2. 餌: 視界 (120 FU) 内の最寄りの浮遊フラグメントへ向かう (獲物がその半分より近くにいる場合を除く)。
3. 獲物: 実効的な大きさが自分以下 (ただし大きさが 1/4 以上) の個体へ向かい、前方 15 度、射程内で
   ティアの確率で撃つ (プレイヤーを AI が操作するときは必ず撃つ)。プレイヤーに対しては:
   - 自分の `fleeFarPct` 倍まで大きくても獲物として向かっていく (レベル 5 以降は 2 倍の自機に向かってくる。
     近づいて 40 FU 以内で `fleeNearPct` を超えると脅威に転じて離れるので、撃ちながら距離を取る)。
   - 自分の 1/`preyMinRatio` (2 / 2 / 3 / 4 / 4 / 6 / 6 / 8、レベル 1〜8、以降 8) 以上の大きさの
     ときだけ狙う。序盤は 2 倍超の敵が自機を無視する。
   - `playerSightFU` (130 + 20 (レベル − 1)、上限 250 FU) で見つけ、距離を `playerBiasPct`
     (110 + 10 (レベル − 1) %、上限 220) で割って近く見せる (他の獲物より優先)。
   - 偏差射撃 (`AI_LEAD`、レベル 3 以降): 弾の飛行時間 (距離 ÷ 弾速、最大 3 秒) × 獲物の速度だけ先の点を
     狙って旋回し、その点が前方 15 度に入ったら撃つ。
   - 群れ (`AI_PACK`、レベル 4 以降): 90 FU 以内に自機を追っている敵がいれば、餌や他の獲物より優先して
     自機を狙う (相手の `aiMode` / `aiTarget` を読むだけで状態は持たない)。
   - 回り込み (`AI_FLANK`、レベル 5 以降): 自機の正面 ±30 度にいて 30 FU より遠いときは、自機そのものでは
     なく自機の横 40 FU (自分がいる側) を目標に旋回する。射線から外れて側面に入る。撃つ判定は自機の方向で行う。
4. 餌でも獲物でも、目標が 30 FU 以内にあって進行方向から 60 度以上ずれているときは
   ブレーキを踏んでクイックターンで向き直る (旋回半径が大きくて回り続けないように)。
5. 回避: 短時間に `evadeHits` (レベル 1: なし、2: 3 発、3〜5: 2 発、6 以降: 1 発) 被弾すると `evadeTicks`
   (2～3 秒) の間、射手 (`evadeFrom`) に対する機動に入る (`evadeMode`)。射手の実効的な大きさが自分の
   2 倍以下 (`AI_COUNTER_MAX_RATIO_PCT`) で体力が 1/4 より多ければ `counterPct` (レベル 1: 0、2: 25、3: 50、4: 60、5: 75、6: 85、7 以降: 100 %) の
   確率で**反撃**、それ以外は**離脱**。回避中にさらに被弾すると射手を更新し、残り時間を 1 秒以上に保つ。
   最初のスフィアでは撃っても逃げられない (初見で「ひたすら逃げられる」を避ける)。
   - 離脱: 逃走方向は射手への方向に垂直な向きに射手から離れる成分を 1/2 混ぜたもので、判断ごとに
     計算し直す。左右は開始時の進行方向に近い側 (ほぼ正面/背面のときはランダム) を選び、残り時間が
     半分になったところで反対側へ切り替えてジグザグにする。逃走方向まで 45 度以上ずれている間は
     ブレーキでクイックターンし、向いたらレベルに関係なくダッシュする。
   - 反撃: ブレーキでクイックターンして射手へ向き直り (45 度以内になるとブレーキを離す)、
     前方 15 度・射程内なら確率によらず撃つ。30 FU より遠ければダッシュで突進する。
   - 射手が死んでいれば `evadeDir` へ旋回してからダッシュする。
   一定方向へ逃げ続ける敵を撃ち続けるだけの単調な展開を断ち切り、狙いを付け直させる。
6. それ以外はゆっくり向きを変えながら巡航する。
7. 恨み (`Entity::grudge`、`GRUDGE_*`): 自機の弾が当たるたびに 1 秒分を加算し、毎 tick 1 減る。
   3 秒分 (`GRUDGE_ON`) に達した時点で 8 秒分 (`GRUDGE_MAX`) に満たし、以後は当たるたびに満たし直す
   (撃つのをやめても 5 秒は追ってくる)。3 秒分以上ある間は、体格差・視界 (400 FU まで探す)・ティアに
   関係なく自機を獲物にし、自機を脅威と見なさず、射程に入れば必ず撃ち、ダッシュで詰める
   (獲物へのダッシュは全般に、進行方向が獲物の 45 度以内に向いてから)。回避 (離脱・反撃) の発動と
   進行はこれより優先で、回避が終わったあとに恨みが残っていれば追跡に入る。
   格上の敵を視界外の後方からミサイルで撃ち続けて倒す戦法を封じるため。

### 近傍探索

エンティティと浮遊フラグメントはそれぞれ「n.z でソートした添字配列」を毎 tick 保つ
(前 tick の順序を引き継いで挿入ソート)。距離 d 以内の候補は z の帯
`|Δz| <= d << 13` の二分探索で絞る。衝突、捕食、被弾、AI の視界がこれを使う。

### 描画 (render)

- 座標系はプレイヤー位置を原点とする FU。精度を保つため、
  すべての位置は整数 units で差をとってから使う。エンティティの本体・浮遊フラグメント・弾は
  整数のまま (units、方向は sim の Q30 単位ベクトル) 頂点を作り、ShapoGFX には
  `FixedVertex` (16.16 FU = units << 8) で渡す (「render 層の整数ジオメトリ」)。
  エフェクト・マーカー・オーラなどは float の FU で作る。
- 1 フレームは `beginFrame()` で組み立て、`renderBand(dst, y, h, dstY)` で
  行範囲を描き、`endFrame()` で閉じる。帯は何度呼んでもよいので、
  フレームバッファを持てない機器では帯単位で転送できる。
  帯に分けて描いた結果は 1 枚で描いた結果とビット単位で一致する
  (端数の帯を含めて sim_test.cpp の `testRenderBands()` で検証している)。
- **`renderBand()` は `sim::Game` を一切参照しない。** HUD が必要とする値は
  `beginFrame()` が `HudState` に写し取る。これにより、シミュレーションを別コアで
  進めながら帯をラスタライズできる (Xiamocon 版がそうしている)。
  `beginFrame()` 中だけは `Game` 全体を読むので、その間 tick は進めてはならない。
- HUD 以外はすべて ShapoGFX の 3D シーンとして描く (帯単位の描画のため)。
  星は `POINTS` (視点から 1500 FU の天球上)、スフィアのワイヤーフレームは `LINES`、
  エンティティ・浮遊フラグメント・弾は三角形、破片と塵は `LINE_LOOP` / `LINES`。
  線と点も三角形バッファのレコードを 1 つ使うので、ワイヤーフレームは 1100 本を上限とする。
  描画順: 背景 (黒) → 3D パス (クリア無効、深度で隠線消去。地平線マーカーはその最後に加算合成で) → 敵の体力ゲージ → HUD。
- **3D パスは 4 つのレイヤに分かれる** (ShapoGFX の `beginLayer()`)。奥から順に
  星 → スフィアのワイヤーフレーム → 地表に立つもの (エンティティ・破片・弾・エフェクト)
  → 画面空間のオーバーレイ (オーラ・体力警告・地平線マーカー)。Z ソートは
  各レイヤの内側で閉じる。地表に立つものは必ずワイヤーフレームより手前にあり、
  オーバーレイは視点の 1.9〜2.0 前の平面にあるので、この前後関係は幾何から確定している。
  星・ワイヤーフレーム・オーバーレイは `LayerFlags::NO_DEPTH` (深度平面もソートも持たない)。
  詳細と検証結果は impl/xiamocon/SPEC.md の「レイヤ分け」を参照。
- スフィアは正二十面体を再帰分割して描く。**分割段数は「面が画面上で何 px になるか」だけで決める**
  (3.1)。自機からの距離ではない — 網の細かさはカメラと球の幾何の問題で、第三者である自機は関係しない。
  カメラの直下点から角度 ψ 離れた地表の点は、視点までの距離と傾きがどちらも ψ だけで決まる
  (C は球の中心から視点までの距離):

  ```
  d(ψ)² = C² + R² − 2 C R cos ψ        cos i = (C cos ψ − R) / d
  ```

  辺 s のセルが画面上で覆うのは `s × focal × √(cos i) / d` px (片方向だけ縮むので平方根)。
  したがって欲しい段数は cos ψ だけの関数になり、面ごとの判定は**カメラ方向との内積 1 回と
  しきい値との比較**で済む (`wantLevel()`、しきい値は `sphereConstants()` が毎フレーム作る)。
  - しきい値は、段数 L と L−1 の境目 = `g(u) = cos i / d² = (c u − 1) / (c² + 1 − 2 c u)^{3/2}` が
    `2^{2(L − 0.5 − K)}` になる u (`K = log2(ICO_EDGE × focal / 目標 px)`、c = C/R)。
    両辺を 2 乗すれば多項式なので、二分探索 12 回に平方根も三角関数も要らない。
    面自身の角半径のぶん広げた `cos(ψ + 角半径)` を段数ごとに表にする (加法定理で 2 乗算)。
  - **地表近くでは足元から地平線まで距離が大きく変わるので網は急に粗くなり、遠ざかるほど
    d と cos i が見える範囲で変わらなくなるのでしきい値が可視範囲の外に出て、網は自然と均等になる**。
    遠くから見下ろすスフィアに密度差を付ける意味は無いという幾何が、そのまま出る。
    段数の幅は `SPHERE_LEVEL_STEPS` (5 段) まで。最も細かい段 (カメラ直下) は
    ±0.65 段の不感帯を持たせて保持する (`sphereTop_`)。境目に座ったカメラで網全体が
    往復しないため。しきい値自体は連続なので、この不感帯は絵の精度を落とさない。
  - 測る基準はダッシュやブレーキを除いたカメラ (`camAltitude_` = フレーミング距離 × レンズ倍率
    + 高度、`camFocalNominal_` = レンズだけの焦点距離)。1 秒に何度も動かせるダッシュで
    網を作り直さないため。**視錐台のカリングは本物のカメラで行う**。
- **画面の外は捨てる (3.1)**。視点を通る画面 4 辺の平面を用意し、面の全体がどれかの外側にあれば
  その部分木ごと捨てる (`camQ_.cullN` / `cullPlane`、地平線カリングと同じく内積 1 回と比較 1 回)。
  低いカメラでは地平線の内側の大半がカメラの後ろか横で、しかもそこが最も近い地表なので、
  これが無いと**描かれない面に予算を使い切ってしまう** (480x320 で歩く辺 2268 → 1116、
  描く辺は 780 のまま)。面の張り出しは `sin a + (1 − cos a)` で上に見積もるので、
  画面にかかった面を捨てて部分木ごと欠けることはない。
- **セルの大きさは `SPHERE_TARGET_PX` (既定 24 px) 固定で、線の予算は天井として働く (3.1)**。
  本数は px の 2 乗に反比例するので、これがそのまま網のコストの調整つまみになる。
  プラットフォームは `DEVOURSPHERE_SPHERE_TARGET_PX` で上書きできる
  (PicoSystem は 48。impl/picosystem/SPEC.md「スフィアの網」)。
  前のフレームが上限を超えたら目標 px を `√(本数/上限)` で大きくし、上限の 70% を切っていれば
  毎フレーム 2% ずつ元の大きさへ戻す。予算を目標にして追い込むと、**スフィアが画面外に出たとき
  (上昇演出) に本数が少ないという理由だけで網が細かくなる**ので、天井にした。
  これで網はカメラの幾何だけで決まり、通常のプレイでは制御が動かない。
  自機の大きさ 2^2〜2^20 で描く辺は 480x320 で 581〜760 本 (上限 1020)、240x240 で 308〜367 本平均
  (上限 510)、セルは常に 24 px。段数の変化は自動操縦 30 秒で 0〜1 回、3 秒ごとに倍化させ続ける
  60 秒でも 1 回。飛行中も同じ規則のまま (下記)。
  3.0 では自機からの距離で決めていたため、大きな自機では予算の 4% (45 本) しか使えず不自然に粗く、
  遠くから見たスフィアでは自機の近くだけ密度が高くなっていた。
  地平線の向こう側の面は捨て、地平線をまたぐ辺は地平線で切る。
  線は頂点色で距離に応じて暗くする (60 FU で最も明るく、900 FU で黒)。
- **飛行中 (LAUNCH / ARRIVE) の例外はほとんど残っていない (3.1)**。網の規則は地上と同じで、
  カメラが遠ざかれば幾何がそのまま均等な網を出す。残るのは 2 つだけ:
  最も粗い段の下限を 3 段 (辺約 68 FU) にする (2 段では遠くのスフィアの縁が 24 角形に見え、
  3 段で円に見える) ことと、上限本数を画面の取り分ではなく配列いっぱい (`MAX_WIRE` の 80 本手前)
  にすること (演出中は他に描くものがほとんど無い。余分な高度 0〜100 FU で直線的に混ぜるので、
  着地で予算が一段で戻ることはない)。実測で上昇から着地まで描く辺は 0〜877 本
  (スフィアが画面外にある間は 0)、セルは 24 px のまま、段数の変化は 1 回。
  線の減衰は巡航高度からの余分な高度だけ手前から始める (`wireFadeOffset_`): 900 FU 上空から
  見たスフィアが黒く消えず、最寄り点から奥へ向かって暗くなる。
  地上 (余分な高度 0) ではどれも効かないので、プレイ中のフレームは変わらない
  (固定条件 2100 フレームのハッシュで確認)。
- **線を描くのは、その線で分かれる 2 面の最小共通祖先**。つまり各ノードは
  「自分の 4 つの子を区切る 3 本」だけを描き、自分の外周は祖先に任せる。
  メッシュのどの線も、それで分かれる 2 面を別々の子に持つノードがただ 1 つ存在するので、
  **同じ線が二度描かれることはなく、重複除去も不要**。祖先を持たない
  正二十面体自身の 30 辺だけは、20 面を走査したあとにまとめて描く。
  この方式にはもう 1 つ利点がある。3 本を描く時点で、その両側の子が
  どこまで細かく分割されたかが**戻り値として分かっている**ので、線を細かい側に
  合わせた折れ線として描ける。異なる分割段数が隣り合う箇所 (T ジャンクション) で
  直線の弦と球面上の折れ線が二重に見える問題が、これで無くなる。
  戻り値は 3 辺ぶんの段数を 4 ビットずつ `uint16_t` に詰めたもの。
- エンティティはコアとフラグメント (と分身) を凧型 4 頂点 (2 三角形) の平面ポリゴンとして投入する。
  距離順に並べ、ワイヤーフレームの後に残った三角形バッファ (予備 220 を除く) を予算として
  近い個体から全フラグメントを描き、予算を超えた個体や画面上で小さい個体 (半径 6px 未満) は
  体の大きさの凧の輪郭 (`LINE_LOOP`) に落とす。アップグレードを持っている敵の輪郭は敵の色ではなく
  白で描く (遠くからでも持ち主が分かる)。さらに小さいものは点。
  この 6px と、輪郭にコアを足す 4px、体力ゲージを出す 2.5px の 3 つの閾値は、
  画面の高さが 240 (`LOD_REF_H`) より低いときはその比で小さくする (`Renderer::lod()`)。
  視野角は縦基準で固定なので画面上の半径は画面の高さに比例し、
  240x135 では 0.5625 倍になって目の前の敵まで輪郭に落ちていた。
  高さ 240 以上の画面では 1 倍のままで、既存のターゲットの絵は 1 画素も変わらない
  (240x240 / 320x240 / 480x320 / 640x360 で確認)。
  1px 未満を点に落とす判定はスケールしない。画素の実態の話であり、
  下げても 1px 未満の三角形になるだけだから。
- 機体の姿勢: `bank` で進行方向まわりにロールする。個々のフラグメントはローカル X 座標の絶対値が
  大きいほど (体の半径に対する比で) 外側が下がるように進行方向まわりに最大 35 度傾ける
  (下反角)。体に厚みがあるように見え、真横から見ても翼が線につぶれない。
  浮遊フラグメントはカメラから見た仰角が浅いときに法線をカメラ方向へ起こす。
  プレイヤーの体に加わらない (大きさが 1/32 未満の) 浮遊フラグメントは白で描く (触れると回復)。
  被弾・吸収の瞬間 (破片が出るのと同じタイミング) は体全体が 0.12 秒光る (敵は白、自機は赤)。
  色はプレイヤーが青緑 (浮遊フラグメントと同じ)、懸賞首 (`Entity::bounty`) がオレンジがかった黄色
  (`PAL_ENEMY_BOUNTY`、大きさによらず)、それ以外はプレイヤーより大きい敵がピンク、それ以下の敵が水色。
  敵はこの 3 色のどれかで、1.x にあった最大の敵の黄色い縁取りは無い。出現直後の無敵時間中は点滅。
  敵の上には体力ゲージを描く (3D パスの後、HUD の前)。
  地平線の向こうにいる敵のうち大きさがプレイヤーの 1/4～4 倍のものは、
  その方向の地平線上に敵の色の三角形で示す。三角形の頂点はスフィアの中心を指す (3.1、`Marker2D::down`)。
  画面上でスフィアの中心に向かう向きは、中心を通る直線がすべて集まる 1 点 (`markerFocus_`、
  投影は直線を直線に写すので毎フレーム 1 回投影するだけでよい) への向きとして求め、
  マーカーごとには `atan2Brad` を 1 回引く。中心がカメラの後ろ (飛行中に上を向いたとき) では
  投影が向きを裏返すので、符号を持っておいて逆向きに使う。アップグレードのアイコンは従来どおり立てる。マーカーは視点の 1.9 FU 先の平面に置いた
  加算合成の扇形として 3D シーンの最後に描くので、地平線付近を飛ぶ敵を隠さない
  (加算なので暗い縁取りはなく、持ち主の白い縁取りだけが線で出る)。色は地表に沿った距離で薄くなり
  (地平線で 100%、球の中心から見て 75 度離れた位置で 25%)、それより遠い敵は示さない。
  ただし自機の順位が 5 位以内のときは、自機より大きな敵 (残りの目標) はどれだけ遠くても示す。
  アップグレードを持っている敵と懸賞首は大きさ・距離によらず必ず示し、マーカーの枠 (40 個) を
  浮遊アップグレードの次に優先して確保する (ほかの敵は残りの枠、最大 32 個)。マーカーの色は体と同じ
  なので懸賞首のマーカーは黄色で、距離のフェードを掛けない (球の裏側にいても全輝度。25% では黒に埋もれる)。持ち主の三角形は (その体と同じく) 白い線で縁取り、縁取りの明るさも
  塗りと同じ距離のフェードに従う。飛行演出 (LAUNCH / ARRIVE) の間は敵・アップグレードともマーカーを
  出さない (`buildScene()` が集めない)。
  ほかの敵は暗い縁にする。
- 弾は加算ブレンドの小さな凧 (バルカン、ミサイル) と細長い四角形 (レーザー、長さは
  `base * 24 + 8 FU` を上限として弾の先端から後方へ伸び、発射後に飛んだ距離より長くはならないので
  銃口から伸びていくように見える)。自分の弾は自機と同じ青緑、敵の弾はピンクがかった赤。
- 破片: sim は被弾・吸収・命中の位置を tick ごとのエフェクトキュー (`Game::effects()`、最大 16 件) に
  記録する (対象のエンティティの添字も含む)。描画側はこれを 1 tick につき 1 回読み、
  小さなワイヤーフレームの三角形 (1 件につき 1～3 個、最大 64 個) をランダムな方向へ飛ばす。
  自機から 90 FU 以内でエンティティが撃墜または吸収されて消えたとき (と自機の死亡時) は
  相手の大きさに応じた大きめの破片を 14 個ばらまく。
- 取り込みの演出: 青緑のフラグメントが体に加わった tick (敵からの吸収を含む。白い回復用フラグメントでは
  出さない) に、視線に垂直な自機色の大きな
  三角形 (半径は体の 5.5 倍から 0.5 倍へ) が回転しながら 0.3 秒で自機へ収縮する (`LINE_LOOP`)。
  アップグレードを取ったときは同じ演出をアップグレードの色で、1.8 倍の大きさ・0.6 秒で出す。回転しながら 0.7～1.3 秒で縮んで消える。自機が受けたものは赤、
  敵に与えたものは灰色。破片の運動は描画側の float 計算で、決定性には関係しない。
- ダッシュの塵: ダッシュ中、自機の前方 (カメラ距離の 4 倍 + 10 FU 先まで) に毎秒 90 × dashLevel 個の塵を
  世界座標に固定して生成し、自機の移動で手前へ流れる。各塵は現在位置から進行方向へ
  `速度 (FU/s) × 0.18 + 1 FU` 伸びる加算ブレンドの線 (先端が明るく末尾が黒) で描く。
  カメラの後ろに回るか 4 秒経つと消える。エフェクトの座標は自機基準なので、
  自機が動いた分だけ毎フレーム逆方向にずらして世界に固定する。
- カメラは後方上空の三人称で、およそ 45 度の俯角で見下ろす。体の大きさはフラグメントの配置ではなく
  `halfSize(log2 size) * (2 + 0.2 * フラグメント数)` で見積もり、配置の揺れがカメラに伝わらないようにする。
  素の距離は `3.5 * 見積もり + 8 FU` (最低 11 FU)、高さは距離と同じ、注視点はやや前方下。
  ダッシュ中は `dashLevel` に応じて後方近く (最大で距離 0.55 倍、高さ 0.22 倍) に下がり、
  進行方向の遠くを注視して視野が 10/70 狭まる。ブレーキで引いて視野 82/70 倍。
- **ダッシュのカメラは自機が育つと効かなくなる (3.1)**。カメラを引き寄せて地面に近付ける
  この演出は、小さいうちは速度感そのものだが、大きな自機では目の前がすぐ地平線になる。
  巡航時の広い視界 (後方も含む) を保つほうが大事なので、`dashLevel` に掛ける係数を
  ゲーム開始時の大きさ (2^2) から `DASH_CAM_OCTAVES` (13) 回の倍化で 1 → 0 に落とし、
  2^15 以上では**ダッシュしてもカメラは一切動かない** (距離・高さ・視野・注視点のすべて)。
  ダッシュそのもの (速度・塵・ゲージ) は sim のもので変えない。
  大きさ 2^16 の自機のダッシュ中、地表に沿った地平線までの距離は 133 FU (3.0) →
  186 FU (レンズだけ) → 362 FU (巡航時と同じ) になった。
- **レンズ (3.1)**。スフィアの半径は一定なのに自機は育つので、大きな自機のカメラは小さな世界の
  高いところに立つことになり、数体分先で地表が落ち込んで画面全体が魚眼のお椀になる
  (カメラが地面に近付くダッシュ中が最も強い)。そこで**自機が育つにつれて視野を狭め
  (`CAM_FOV_REF` 70 度 → `CAM_FOV_LONG` 45 度)、その分だけカメラ装置全体 (距離・高さ・注視点) を
  後ろへ下げる**。素の距離が `CAM_LENS_DIST0` (16 FU、最小の自機を見る距離) を超えたところから効き始め、
  そこから `CAM_LENS_OCTAVES` (2.5) 回倍になったところで狭め切る。下がる倍率は
  `tan(70/2) ÷ tan(視野/2)` なので、これだけなら自機は画面上の同じ大きさ・同じ位置に留まり、
  変わるのは遠近感の付き方だけ。そこにさらに `CAM_OPEN` (最大 1.25 倍) 引いた分が、
  見渡せる範囲の広がりと地平線の後退になる。大きさ 2^16 の自機で視野 70 → 47 度、
  距離 81 → 162 FU、地表に沿った地平線までの距離 270 → 362 FU (ダッシュ中は 133 → 186 FU)。
  最小の自機では視野 70 度・距離とも従来どおりで、描く図形の数も変わらない。
  - 距離と高さは「基準レンズ (70 度) での距離」= **フレーミング距離** で保持・補間し
    (`camFrame_` / `camFrameH_`)、レンズの倍率を掛けて実際の距離にする。自機の画面上の
    大きさはフレーミング距離だけで決まるので、レンズがどう動いても体の大きさは動かない。
    スフィアの分割段数の基準距離 (下記) もこのフレーミング距離なので、網の密度も変わらない。
  - レンズ (`camLens_`) は 1.5/s とゆっくり補間する。自機の見かけの大きさはレンズに依らないので
    急ぐ理由がなく、スフィアの切り替え (フレーミング距離は飛ぶが、そこで自機が一気に小さくなる)
    でも星空が一瞬でズームせずに 2 秒ほどかけて戻る。実測でレンズの 1 フレームの変化は最大 1.4%、
    自機の見かけの大きさと視線方向の 1 フレームの変化は切り替えを含めて変更前と同じ。
  - ダッシュとブレーキの視野はレンズに対する**倍率** (`camFovMul_`、5/s で補間) で、
    こちらは距離で打ち消さない。ズームして見せるためのものだから。
  旋回で最大 9 度 (ブレーキ中 14 度) ロールする。値は指数関数的に補間する。
  `DEVOURSPHERE_CAMERA_ROLL=0` (renderer.hpp、既定 1) でビルドするとこのロールだけを止める。
  機体の `bank` は sim のものなのでどちらでも同じように傾く。
  デバイスを傾けて操作するプラットフォーム (M5StickS3 版) 用で、
  手の中で画面が既に傾いているところにカメラまでロールさせると傾きが二重になる。
  タイトルではプレイヤーの周りを回る。
- **飛行中のカメラ (LAUNCH / ARRIVE)**。自機の frame を飛行経路に沿ってピッチさせた基底
  (`flightFwd_` / `flightUp_`、右軸まわりの回転。ピッチは `atan2(playerClimb, speed)` を 4/s で
  指数補間した `camPitch_`) を、機体の描画 (`drawEntity()` の自機だけ、`playerPitchBrad_`) と
  ダッシュの塵の発生方向に使う。上昇の終わりで約 70 度、降下の初めで約 -75 度。
  スフィアの切り替えで上昇から降下に変わるとき、この補間で機体が横から見て「次のスフィアへ
  頭を下げる」動きになる。
  カメラもこの基底で置く。切り替えで飛行方向が変わらなくなったので、基底は切り替えを通して
  連続 (以前は速度が 150 度折れるのを cos²(orbit) の混合でごまかしていた)。
  カメラはこの基底の up まわりに自機を回る (`camOrbit_`、0 = 後方、π = 前方。台本を 8/s で追う。
  角度なので差を (-π, π] に畳んで近い側から追い、値も畳んでおく):
  - LAUNCH: 最初の 1.5 秒はプレイの角度のまま (離陸を見せる)。1.5〜5 秒で後方 → 横 → 前方へ
    smoothstep で回り込み、同時に距離を飛行用の距離まで引き、高さを距離の 0.35 倍
    (飛行経路から約 19 度上) に下げ、注視点を自機に合わせる。前方に着くと自機の向こうに離れた
    スフィアが画面中央に見える。
    飛行用の距離はプレイの 1.25 倍だが、**切り替えでスフィアが縮む前**
    (LAUNCH と `switchPending()` の ARRIVE) は「縮小後の自機がその飛行用の距離で写るのと同じ
    見かけの大きさになる距離」にする。プレイの距離 `3.5 × 半径 + 8 FU` の定数 8 FU のせいで、
    小さな自機ほど画面上では小さく写る (2^14 → 縮小後で 1.7 倍、最大級では 2.8 倍) ので、
    縮小後の距離にスナップすると自機が急に小さくなって見えた。縮小後の大きさは
    `playerSizeAfterSwitch()` (フラグメントの指数を同じだけ下げた合計、フラグメント数は不変) で
    描画側が前もって求める。2^14 の自機なら 60 FU から 130 FU、2^18 なら 110 FU から 260 FU まで
    回り込みの間に引く。切り替えの瞬間の見かけの大きさ (半径 ÷ カメラ距離) は 0.112 → 0.112 で
    連続 (その後フラグメントの合体で見積もりが数 % 動く分は通常の補間)。
  - ARRIVE: 0〜2 秒で前方 → 横 (ちょうど 1 秒、切り替えの tick) → 後方。LAUNCH と**反対側**を
    回るので (π → 2π)、LAUNCH と ARRIVE で自機の周りを 360 度一周する。横にいる間は
    どちらのスフィアも画面外 (前後のスフィアの中心は視線から約 90 度、半径は 20〜30 度)。
    最初のスフィア (メニューから入ったとき) は orbit と pitch もスナップして、前方から始める。
    後方に着いてから 3.5 秒までに高さを距離の 0.65 倍まで上げ (急降下中の機体を上から見せる)、
    3.5〜5 秒でプレイの角度・距離・注視点に戻す。
  - スフィアが切り替わった (`sphereSeed()` が変わった) フレームでは距離・高さ・注視点と
    ピッチを目標値に**スナップ**する。自機が縮んでいるので補間すると画面上の自機がズームして
    見える。ピッチは sim が frame を回した分だけ値が変わる (+75 度 → -86 度) が、新しい frame に
    新しいピッチを掛けたものは元の飛行方向そのものなので、スナップすると画面上は何も動かない。
    補間すると逆に機体が一回転してしまう。エフェクト (塵) も原点の移動分をずらさない。
    そのときどちらのスフィアも画面外なので飛びは見えない。orbit は補間を続ける。
    飛行中のカメラの向きの変化は切り替えを含めてどこでも毎フレーム 2.5 度以下。
  - スフィアの分割の基準距離は引きを含まない自機の公称距離のまま。切り替えのフレームでは
    `sphereCountValid_` を落として段数を探し直す (自機が縮んで基準距離が一気に変わるので、
    前のフレームの本数から決めると 1 フレームだけ 2 倍の本数になる)。
  - ダッシュの塵は飛行中も出す (PLAYING / LAUNCH / ARRIVE)。線の向きは接線ではなく
    実際の速度 (接線 × speed + 法線 × playerClimb) に沿わせる。地上では climb が 0 なので
    従来と同じ式を通る。線の長さはカメラ距離の 1.5 倍で頭打ち (小さな自機が 300 FU/s で
    降下すると、カメラ距離の 3 倍の線になる。地上では届かない)。
- HUD のレイアウトは絶対座標を持たず、フレームバッファの大きさから起動時に決める
  (`UiMetrics`)。基準画面 480x320 に対する縮尺 `scale8` (1/8 単位、短い方の軸で決める)
  を持ち、余白・ゲージ・アイコン・マーカー・敵の体力ゲージ・オーラの半径など「見た目の
  大きさを保ちたい」距離は基準画面の値にこれを掛ける。画面いっぱいに出す文字 (タイトル、
  武器選択、死亡画面) の縦位置は高さに対する比で置くので、アスペクト比に追従する。
  フォントは 8 / 12 / 21px の 3 種類を整数倍して使い、基準の 1/2 未満の画面では各役割が
  一段小さいフォントに落ちる。倍率 (`fontMult`、TITLE は広い画面でその 2 倍) は 240x240 以下の
  画面では常に 1 で、2 以上になるのは M5Tab5・WASM・CLI だけ。ShapoGFX の gfx2d には文字の
  整数倍率が無く、拡大は変換 (`setTransform()`) で行うので、文字は `textWidth()` /
  `textLineAdvance()` / `textLineHeight()` / `drawText()` (renderer.hpp、倍率を引数に取り
  画素で返す) を通す。倍率 1 では変換に触れないので、`SHAPOGFX2D_TRANSFORM=0` の
  ビルド (小さい画面の 4 機種) でも同じ画素になる (固定条件のハッシュで確認、2026-09-24)。
  変換が無いビルドで倍率 2 以上が来たら、拡大せずに正しい位置へ描く。
  `Renderer` の中では `setHudFont()` が倍率を `textScale_` に覚え、`textW()` / `lineAdv()` /
  `lineBox()` / `putText()` がそれを使う。これは描画 (帯) 側の状態なので、帯の外で呼ばれる
  `showTable()` のレイアウトは倍率を引数で渡す。それでも収まらない文字列は短い代替文字列に差し替え、
  それも収まらなければ描かない。武器選択は列幅が足りなければ縦並びに切り替える。
  スフィアのワイヤーフレームの上限本数も縮尺に比例して減らす (増やす方向には、
  三角形バッファの容量があるので 1100 本のまま)。
- **HUD の安全域 (`setHudInsets()` / `HudInsets`)**。仮想パッドのように、プラットフォームが
  自分でフレームの一部を覆う場合、その分を渡すと HUD がそこを避ける。世界に貼り付いているもの
  (3D シーン、敵の体力ゲージ、地平線マーカー、被弾時の画面の縁) は避けない。移動するのは HUD だけ。
  `top` / `bottom` は端に寄せて描く行すべてを内側へ動かす。`left` / `right` は
  **画面下の左右の隅にあるパッド**を表すので、下端の行 (アップグレードのアイコン、予備コア、
  バージョン、操作ヒント) にだけ効く。上端の行と画面中央に出す文字は、上の隅を覆うものが
  無いのでフレームいっぱいのまま。`UiMetrics` の縮尺はフレーム全体の大きさから決めたままなので、
  パッドがあるからといって文字が小さくならない。入りきらない行はこれまで通り短い代替文字列に
  なるか描かれない。既定は全部 0 で、M5Tab5 版以外は指定しないので見た目は変わらない
  (指定なしのときフレームハッシュが一致することを確認済み)。`setControlHints()` と同じく
  `init()` をまたいで保持されるが、値はフレームの画素なので解像度を変えたら指定し直す。
- HUD: 左上に体力ゲージ、その下に順位。上中央にスコア。順位の行は、PLAYING 中に自機が 1 位で懸賞首が
  残っているときは `RANK 1 / N` の代わりに懸賞首の色 (黄) で「KILL THE BOUNTY」(2 体以上なら
  「KILL n BOUNTIES」、狭ければ「BOUNTY xn」) を 1 秒周期 (0.5 秒表示・0.5 秒消灯、`blinkOn`) で
  点滅させ、懸賞首を全滅させて LAUNCH を待つ 4 秒の間は `RANK 1 / N` に戻して同じ周期で点滅させる
  (`HudState::bountyCount` / `playerAlive`)。
  体力ゲージの長さ (自機も敵も) は切り上げで求める: 体力が残っている限りゲージが空にならない
  (切り捨てだと体力がわずかな敵がゲージ 0 のまま飛び続けて見える)。
  デバッグモード (`Game::debugMode()`、WASM 版が URL で入る。チート関数のどれかを呼んでも立つ。
  `reset()` では消えない) では上中央のスコアに重ねて大きく半透明の赤で「DEBUG MODE」を出す
  (スクリーンショットの捏造防止)。
  スコアの表示値は実際の値を追いかけて増える: 毎秒、差の 4 倍 (最低 30 点/秒、実際の値を超えない)
  だけ進むので、ステージが進んで加点が大きくなっても同じ時間で追いつく。値が下がったとき
  (ゲーム開始) は即座に合わせる。死亡画面のスコアは実際の値。
  体力ゲージの下に緊急回避の準備状況を細いバー (`HudState::dodgeReadyQ8`) で出す: クールダウン中は
  暗い色で左から伸び、使えるときは明るい水色で満杯。
  右上に残り時間 (PLAYING 中のみ。切り上げの m:ss なので 0:00 は本当に時間切れのときだけ。残り 1 分未満で黄、
  30 秒未満は 0.5 秒ごとに赤と白を切り替える)、その下にスフィアのレベルと武器名。時間切れで残骸を見届けて
  いる間は画面中央に赤で「TIME UP」。LAUNCH の間はそのスフィアの集計を出す: 広い画面では「SPHERE SCORE n」
  「TIME m:ss   BONUS +n」「TOTAL n」の 3 行、狭い画面 (`compact`) では「+n  m:ss  +n」の 1 行。
  タイトルと死亡画面のハイスコアには到達スフィアを添える (「HIGH SCORE n  SPHERE k」、狭ければ「HI n Sk」)。
  core のバージョン (`VERSION_STRING`) は全画面で画面下中央の最下行に出す (スクリーンショットに写るように。
  `drawVersion()`)。タイトルとポーズの操作案内はその分 1 行上に詰める。アップグレード状況が出る画面
  (PLAYING / LAUNCH / ARRIVE / DEAD) では、左のピップと右の予備コアの間に入るときだけ描く
  (`upgradeStatusExtents()`。この配置はレベルに依らないので解像度で決まる: 240x240 のように入らない
  解像度ではタイトル画面だけに出す)。
  左下に Shield (縦長の菱形、水色)・Overdrive (三角形、赤橙)・
  Thruster (矢じり、黄緑) のアイコンとレベルのピップ 3 個、右下に予備コア (4 本の閃光星、ピンク) 3 個分
  LAUNCH の最初の 2.5 秒は「SPHERE DEVOURED」(カメラが前方に回り込む前に消す)、
  ARRIVE の 2 秒 (カメラが後方に着く) から 4.5 秒までは大きく「SPHERE N」を画面中央に出す
  (ポーズ中はどちらも出さず、「PAUSED」と重ねない)。
  (残っている分だけ明るい)。被弾時は画面の縁が赤く光る。死亡画面にはスコアとハイスコア、
  タイトルにはハイスコアを出す。
  タイトル画面の下端には操作の案内を 2 行出す。この文字列は入力装置に依存するので
  プラットフォームが `setControlHints()` で渡す (`ControlHints`、既定は PC のキーボード向け)。
  各行には短い代替文字列があり、画面が狭いときはそちらに、それも入らなければ描かない。

- 体力警告: 自機の体力が半分以下のとき、画面の上下左右の縁に赤いグラデーション
  (縁が赤、内側へ黒に落ちる頂点色の四角形、加算合成、視点の 2 FU 先の平面) を描く。
  幅は画面高さの 10%。明るさは体力 50% で 0 から始まり、0% に近づくにつれて 50% まで直線的に濃くなる。
  3D シーンの最後に描くので HUD の下、ほかのすべての上に重なる。
- 浮遊アップグレードは加算合成の立体を回転させて描く: Shield は縦に伸ばした正八面体、Overdrive は正四面体、
  Thruster は矢じり型に伸ばした四面体 (ダート)、Extra Core は星型八面体 (正四面体 2 つ、8 本トゲ)。
  地平線の向こうにあるものは地平線上にアップグレードのアイコン (HUD と同じ形、敵のマーカーと同じく加算合成) で示す。
  立体は片面描画 (裏面カリング) で、重なった面が加算で明るくなりすぎないようにする。
- 気配のオーラ: 自機の近くにいて画面に映っていない敵は、その方向の画面端に
  敵の色のぼんやりした光 (`TRIANGLE_FAN`、中心が敵の色で縁が黒、加算合成) で示す。
  大きさは自機とのサイズ差 (`Entity::size` の比)、濃さは距離で決める。画面上の方向はカメラ座標での
  相対位置から決め、光は視点の 2 FU 先の平面に置く (最大 12 個)。
  - 大きさ: 自機の 1/8 で最小 (半径 20 px)、2 倍で最大 (70 px)、間は対数で補間し、2 倍以上は最大のまま。
    1/8 未満の敵はオーラを出さない (候補にも入れない)。ただし懸賞首 (黄色) はサイズにかかわらず
    必ず候補に入れ、1/8 未満なら最小の大きさで出す。
  - 濃さ: 範囲の端で 0、自機の位置で 1 の線形。範囲から出ていく敵は消えるまで連続的に薄くなる。
  「近く」は FU の定数ではなく視野に対して決める: 範囲はカメラ距離での視野の半分の高さ
  (`camDist_ * tan(fov / 2)`) の 10 倍で、最小の自機で約 110 FU。自機が育つとカメラが引く
  (下記「カメラ」) ので、定数のままだと範囲内の敵がすべて画面に映ってしまい、
  2^16 以上ではオーラが一つも出なくなっていた (3.2 まで)。サイズ 2^12 あたりからは範囲が
  スフィアの大半に及び、画面外の候補が常に 12 体を超えるので、描くのは自機に近い順に 12 体
  (エンティティ番号順に先着 12 体では任意の組になる)。

### メモリ

| 対象 | サイズ |
|---|---|
| `sim::Game` | 84,088B (ARM の実測) = エンティティ 224 x 224B、浮遊フラグメント 512 x 44B、弾 128 x 68B、ほか約 2.3KB。上限を 256 / 1024 / 256 から実測ピークに合わせて絞る前は 136,512B、エンティティを詰める前 (276B) は 95,360B |
| `render::Renderer` | 23,848B (ワイヤーフレームの線分 1100 x 10B = 11KB、破片 64、塵 64、フラッシュ 1KB) |
| 3D アリーナ | 三角形バッファはバイト予算 (1 プリミティブあたり 32 ビットで 52〜96B、必要な属性だけを持つレコードが確保される)。ワイヤーフレームが 2D に移ってからは 240x240 で世界とオーバーレイだけが入るので、PicoSystem 版は 40KB、Xiamocon 版は 64KB。WASM 版は 256KB |

いずれも動的確保をしない。ShapoGFX の gfx2d にはアリーナを渡さない (`Graphics2D::init()` を
呼ばない)。アリーナが使われるのは `pushState()` と 13 辺以上の多角形・回転した角丸矩形だけで、
このゲームはどれも使わない (アイコンの多角形は 8 頂点まで)。`Graphics2D` は帯ごと・関数ごとに
スタックに作り、32 ビットで 112B (ShapoGFX e0f9662 から。それまでは 68B)。
フレームごとの作業用配列は**ローカル変数ではなく `Renderer` のメンバに置く**。
上の表は既定の構成で、配列の上限は次節のマクロで縮められる (ESPboy 版は `Game` 23.5KB、`Renderer` 10.5KB)。
RP2350 では各コアのスタックが 4KB 固定 (SCRATCH_X / SCRATCH_Y にあり拡張できない) なので、
`MAX_ENTITIES` 個の要素を持つ配列をスタックに置くとそれだけで溢れる。
RP2350 (520KB SRAM) では帯バッファを含めて
収まるようにアリーナと上限を調整する必要がある。RP2040 (PicoSystem、256KB) には上限を絞った
`Game` とアリーナ 48KB で載る (impl/picosystem/SPEC.md)。

`Game::reset()` は前のゲームが残したものをすべて消す (スコア、アップグレード、リスポーン待ち、
エフェクト、そして状態を TITLE にしてからスフィアを作る)。
同じオブジェクトを `reset()` し直した結果は、新しく作ったオブジェクトと bit 単位で一致する。
残るのはハイスコア (表示用) と `debugAutoPlayer` のフラグだけ。

### HUD の帯ごとのスキップ

`drawHud()` は帯ごとに呼ばれ、文字列の整形と幅の計測 (`textW()`) を帯の数だけやり直す。プレイ中の HUD は
上の帯 (ゲージ、スコア、順位、右上の時間・スフィア・武器) と下の帯 (アップグレードの状態、バージョン) に
しかないので、`hudBandIdle()` が「この帯の行は上下の帯域の間にある」と判定したら描かずに返る。
被弾の枠、飛行と死亡の表示、ポーズ、序盤のヒント、DEBUG MODE のある状態では判定しない (常に描く)。
帯域の境界は各要素の行に 1 行の余裕を足したもので、出力は変わらない (固定条件のハッシュで確認、
2026-09-22)。8 帯の 128px 画面 (ESPboy) では host の `renderBand` の 4 割がこれだった。

### 縮小構成のためのビルド時定数

RAM か CPU が足りないターゲット (impl/espboy/SPEC.md) のために、次の定数はマクロで上書きできる。
どれも `#ifndef` で既定値を持ち、指定しなければビルドは従来と bit 単位で同じ
(固定条件のフレームハッシュで確認済み、2026-09-22)。

| マクロ | 既定 | 何を変えるか |
|---|---|---|
| `DEVOURSPHERE_MAX_ENTITIES` / `_MAX_FLOATING_FRAGMENTS` / `_MAX_BULLETS` | 224 / 512 / 128 | `Game` の 3 つの配列。`MAX_ENTITIES` は 256 未満 (1 バイトの添字) |
| `DEVOURSPHERE_INITIAL_ENTITIES` / `_INITIAL_FOOD_FRAGMENTS` / `_FOOD_TARGET` | 200 / 320 / 400 | 人口。`static_assert` で配列に収まることを確かめる |
| `DEVOURSPHERE_SPHERE_RADIUS_SHIFT` | 17 | スフィアの半径 2^n units (17 = 512 FU、16 = 256 FU で表面積 1/4)。15〜17。FU 単位の距離 (視界、リスポーン環、制限時間) は変わらないので、小さい球はゲームの短縮版になる |
| `DEVOURSPHERE_FRAGMENT_KEEP_LARGEST` | 0 | 浮遊フラグメントの配列が一杯のときの規則 (上の「スフィア」の節) |
| `DEVOURSPHERE_MAX_GAUGES` / `_MAX_MARKERS` / `_MAX_ENEMY_MARKERS` / `_MAX_DEBRIS` / `_MAX_DUST` / `_MAX_STARS` | 64 / 40 / 32 / 64 / 64 / 120 | `Renderer` のフレームごとの配列 (8 / 16 / — / 72 / 16 / 24 バイト)。溢れた分は描かれないだけ |
| `DEVOURSPHERE_MAX_WIRE` / `_MAX_LINES2D` / `_MAX_POINTS2D` / `_SPHERE_TARGET_PX` | 1100 / 512 / 256 / 24 | (以前からある。「星とワイヤーフレームは 2D で描く」「2D の線・点・マーカー」「ワイヤーフレームの分割判定」) |
| `DEVOURSPHERE_SUPPRESS_ALPHA` / `_NO_DEPTH` / `_CAMERA_ROLL` / `_TICK_RATE` | 0 / 0 / 1 / 60 | 規則の切り替え (それぞれの節) |
| `DEVOURSPHERE_HOT_ATTR` | (空) | 最内のループ (ワイヤーフレームの DDA と帯の 2D 線、網の走査 `subdivideFace` / `emitChord` / `addWireSegment`、`projectQ`、`normalizeQ30`、`isqrt32` / `isqrt64`) の定義に付ける属性。ESPboy 版は `__attribute__((section(".iram1.ds")))` で IRAM に置く (Xtensa で約 8KB)。ShapoGFX の `SHAPOGFX3D_HOT_ATTR` と同じ発想で、コードの置き場所以外は何も変えない |

### 深度なしの世界 (DEVOURSPHERE_NO_DEPTH)

`DEVOURSPHERE_NO_DEPTH=1` (renderer.hpp、既定 0) でビルドすると、世界のレイヤー (地表に立つもの全部) も
オーバーレイと同じ `LayerFlags::NO_DEPTH` で開く。ShapoGFX はそのレイヤーの記録に深度平面を持たず
(1 記録 12 バイト減)、ソートも深度比較もせず、後から入れたプリミティブが先のものを覆う。
そこで `buildScene()` が自分で奥から手前へ並べる: 浮遊フラグメント → 本体を **遠い順** → 弾 → エフェクト。
既定の構成では本体は近い順に描いていて (三角形の予算を近いものから使うため)、
NO_DEPTH ではその予算の判定だけ近い順に済ませてから (`Vis::full`) 遠い順に描く (`drawVisible()`)。
狂うのは「本体の後ろにあるフラグメントが本体の上に描かれる」「本体の下の弾」程度で、
上から見下ろす場面がほとんどなので本体同士の重なりは稀。ESPboy 版が使う。

### 星とワイヤーフレームは 2D で描く

星 (`drawStars()`) とスフィアのワイヤーフレーム (`buildSphere()`) は 3D パイプラインを通さない。
どちらも深度を持たず、世界にあるものは必ずその手前にあるので、`beginFrame()` で
画面座標に投影して線分 (`WireSeg`: 1/16 画素の int16 座標 4 つと両端の明るさ、10 バイト、最大 1100 本)
と点 (`StarPt`) として持ち、`renderBand()` がクリアの直後、3D レイヤの前に帯へ直接描く
(`drawBackdropBand()`)。

- **走査も投影も整数**。面の頂点は Q30 の単位ベクトル (sim の `Vec3`、`normalizeQ30` / `dotQ30`) で、
  中点は半分ずつ足して正規化する (Q30 の単位ベクトル 2 つの和は int32 を溢れる)。
  カメラは `updateCamera()` の末尾で float から作る整数版 `CameraQ` (視線基底の Q30 ベクトル、
  スフィア中心から見た視点の位置を 1/16 units で、焦点距離と画面中心を 1/16 画素で、
  地平線と間引きの cos 閾値を Q30 で)。表面の点の位置はスフィア半径が 2^17 units なので
  単位ベクトルのシフト 1 回、視点座標は内積 3 つ、透視除算は 32 ビット除算 1 回
  (`projectQ()`)。片方でもニアプレーン手前なら線を捨てる (3D パイプラインがそういう線に
  していたことと同じ)。明るさは視点からの距離 (`isqrt32`) から。
  画面外にはみ出す線分だけ Liang-Barsky で切り詰める (そこだけ 64 ビット除算)。
  星の方向と色も `init()` 後の最初のフレームで一度だけ float で作り、以後は整数。
- 線分配列は `DEVOURSPHERE_MAX_WIRE` (既定 1100) 本。画面の予算 (`UiMetrics::wireLines`) はこれを
  超えない。240x240 の予算は 550 本なので PicoSystem 版は 560 にしている。
- エンティティの詳細度 (`buildScene()`): 三角形バッファの残りから、後に描く浮遊フラグメント・弾・
  エフェクトのための予備 (380 レコード、ただし残りの 1/3 まで) を引いた分を、近い順に本体の
  凧に使う。予備が固定 380 だった頃、32KB のアリーナでは予算が負になり全エンティティが輪郭だけになった。
  1 レコードのバイト数 (フラット、世界レイヤに深度があれば深度付き、エントリ込み) は
  ShapoGFX の `Graphics3D::primitiveBytes()` から取る。以前は 64B (64 ビットのホストは 76B) を
  手書きしていたが、ShapoGFX の更新 (d538138) で 60B になり、手書きの値は更新ごとにずれるため。
  プラットフォームは `Renderer::setDetailTriangles()` で本体に使う三角形数に上限を付けられる
  (0 = バッファの許す限り)。本体は 1 体最大 18 三角形で、FPU の無いコアでは凧 1 つ数十 µs かかり、
  画面内の台数に比例してフレーム時間が伸びる唯一の要素なので、近い順に上限まで本体、残りは輪郭にする。
- 帯への描画は主軸方向の整数 DDA (1/16 画素 × 2^12)。常に線分の始点から数えるので、
  隣り合う帯に描いた断片は正確に繋がる。帯に入る画素の範囲は歩かずに割り算で求める。
  明るさは両端の値を線形補間し、32 段の表でネイティブ画素に変換して書く
  (RGB565_SWAPPED と ARGB4444 は直接書き込み、他の形式は `fillRect` 経由)。
- 3D パイプラインに残るレイヤは「世界」と「画面上のオーバーレイ」の 2 つ。
  線 1 本あたり 52 バイトのレコードと、線が横切るスキャンラインごとのスパンが無くなった。
  RP2040 では線 1 本あたり `beginFrame` で約 240µs (float の頂点変換とセットアップ)、
  ラスタライズでもその細切れのスパンが大半を占めていた。
- 絵は ShapoGFX の線描画と画素単位では一致しない (480x320 の 1 フレームで 153,600 画素中
  約 3,800 画素。線の描画規則と整数投影の丸め) が、同じ線が同じ場所に同じ色で出る。

### 半透明合成の抑制 (DEVOURSPHERE_SUPPRESS_ALPHA)

`DEVOURSPHERE_SUPPRESS_ALPHA=1` (renderer.hpp、既定 0) でビルドすると、3D パイプラインの外で
フレームに重ねる合成をすべてやめる。指定しないときは、地平線のマーカー (敵の三角形とアップグレードの
アイコン) を加算合成で塗り (`fillTriangle2D()` が `setBlend(ADD)` して行ごとに `fillRect()`)、
ダッシュの塵の線分も加算で描く (`L2D_ADD`、線分ごとに `setBlend(ADD)` して画素ごとに `fillRect()`。
黒へのグラデーションが加算では透明へのフェードになる)。どちらも描き終えたら `ALPHA` に戻す。指定したときは、画面外の近い敵を示すオーラ (縁が黒に
フェードする加算合成の扇形、半径 20〜70px、最大 12 個) の代わりに、敵の色で塗りつぶした
不透明な三角形を出す。先端が画面の縁に接して敵の方向を向き、大きさはオーラと同じサイズ差で決まり
(基準画面で 8〜18px、240x240 で 6〜13px)、色はオーラと同じ距離の濃さで敵の色を暗くしたもの。扇形は頂点 13・グラデーション三角形 12・
加算合成の塗り 3,000〜4,000 画素で、FPU の無いコアでは 1 個約 1ms かかり、混雑時に
12 個まで出る。三角形はフラットで不透明なプリミティブ 1 つ。PicoSystem 版が使う。

同じマクロで、マーカーと塵は不透明の塗り (塵は黒との補間) になり、体力警告 (画面の縁の赤いグラデーション、加算合成) も上下端だけ・厚さ半分
(画面の高さの 5%) になる。4 辺のグラデーションは画面の 1/3 を加算合成で塗り、
M0+ では体力が減った途端に 28 → 15fps に落ちた。

### render 層の整数ジオメトリ

エンティティの本体 (`drawEntity()`)、浮遊フラグメント、弾は float を一切使わずに頂点を作る。
位置は `sim::scaleToLength(n, r) - origin_` の units、向きは `frame.t` / `frame.n` とその外積の
Q30 単位ベクトル、長さは units で、`putKiteQ()` / `putQuadQ()` / `putLineLoopQ()` / `putPointQ()` が
`sim::scaleToLength()` で頂点を置いて ShapoGFX の `FixedVertex` (16.16 FU = units << 8) にする。
ShapoGFX の固定小数点パイプラインはこれを変換なしにそのまま読み、float パイプラインは float に
戻すので、どのプラットフォームでも同じ頂点データになる。

- バンクは brad のまま Rodrigues の回転 (`rotQ30()`、入力が単位ベクトルなので再正規化しない)。
  下反角は `side * |x| * degToBrad(35) / bodyR` の brad。
  フラグメントの向きは `normalizeQ30({dx, dy, 0})` で (x, y) 平面の単位ベクトルにする。
- 浮遊フラグメントのカメラ方向への起こしは Q30 の内積 `elev` から
  `k = min(0.8, (0.55 - elev) * 0.8 / 0.55)` を Q30 で作り `normalizeQ30(up + toCam * k)`。
  スピンは sim の `sinQ30` / `cosQ30`。
- 係数は分数にした (1.4 → 7/5、2.5 → 5/2、2.2 → 11/5、0.3 base + 0.08 FU → base * 3 / 10 + FU * 8 / 100 など)。
  float 版とホストで比べると 420 フレーム中 画素の 0.013% が違う (辺の丸め)。
- 可視判定も整数: 視線方向の手前かどうかは units の相対位置と `camQ_.fwd` の内積、
  「画面上で n 画素以上か」は `(s * focal16)^2 >= (px16 * d^2)` の比較で、平方根も除算も使わない
  (`atLeastPx()`)。エンティティだけは詳細度とゲージの閾値に画面上の半径 `px` が要るので
  `isqrt64` 1 回と除算 1 回で作る。`Vis::d` は units の整数。
- 画面外の敵のオーラは全エンティティを見るので、プレイヤーからの距離の判定
  (範囲は視野に比例、上記) を `dotQ30(n, camQ_.player)` と、その範囲の弦が張る角
  (`cos = 1 - 2 (range / 2R)^2`、2% のマージン) の Q30 比較で先に済ませ、通ったものだけ
  float で投影する。小さい自機では大半がここで落ちる。自機が育って範囲がスフィアの大半に
  及ぶと事前判定は素通しになり、全エンティティを投影する (候補が 12 体埋まった後は、
  12 番目より遠いものは投影せずに落とす)。
  地平線の向こうの敵のマーカーの角度は `acos` ではなく sim の `atan2Brad` (sin は既に計算している)。
- エフェクト (破片、取得の閃光) と浮遊アップグレードの図形は float のままだが、`sinf` / `cosf` は
  使わない (src/render/trig.hpp、下記)。破片は生成時に三角形の面の基底 `u` / `v` を決めておき、
  毎フレームは sin / cos 1 組と 120 度回転の恒等式で 3 頂点を出す (`triangleAngles()`)。

### 2D の線・点・マーカー

ワイヤーフレームと同じ経路 (`beginFrame()` で整数カメラで投影して配列に入れ、`renderBand()` で
帯ごとに整数 DDA で描く) を、遠いエンティティの輪郭、破片、取得の閃光、ダッシュの塵、
遠いフラグメント・敵の点、地平線のマーカーにも使う。FPU の無いコアでは ShapoGFX の頂点変換と
セットアップが線 1 本 46µs・点 1 個 49µs・マーカーの扇形 129µs で (RP2040 での実測、
impl/picosystem/SPEC.md「実機の記録」12 回目)、混雑したフレームは線 100 本と点・マーカー数十個を持つ。
2D 経路では 1 本数 µs。

- 線分 (`LineSeg`、14 バイト: 1/16 画素の両端、両端の明るさ、層、RGB565 の色) は
  `DEVOURSPHERE_MAX_LINES2D` (既定 512) 本、点 (`StarPt`) は `DEVOURSPHERE_MAX_POINTS2D` (既定 256) 個。
  溢れた分は従来の 3D 経路に流す (`putLineLoopQ()` / `putLoop2Df()` / `putPointQ()` の fallback)。
- 層は 2 つ。`L2D_UNDER` は 3D 層の前に描く (輪郭と点: 手前の機体に隠れる)、`L2D_OVER` は
  3D 層の後 (破片、閃光、塵、持ち主のフラグメントの輪郭、マーカーの白い縁取り)。
  奥行き判定は無いので、機体の裏側にある破片は機体を透けて見える。
- 明るさが両端とも 255 の線 (ほとんど) は帯ごとにネイティブ色 1 語を作って直書き。
  塵だけ頭 255 → 尾 0 のグラデーションで、`L2D_ADD` 付きなら画素ごとに加算 (透明へのフェード)、
  `DEVOURSPHERE_SUPPRESS_ALPHA` なら黒との補間を不透明で書く (背景がほぼ黒なので見た目は近い)。
- マーカーは `Marker2D` (画面座標) を `renderBand()` が 3D 層の後に三角形 (アイコンは中心からの扇)
  で塗りつぶす (`fillTriangle2D()`、走査線ごとの `fillRect`。既定は加算合成、
  `DEVOURSPHERE_SUPPRESS_ALPHA` なら不透明)。アップグレードのマーカーも敵のマーカーと同じ距離のフェード
  (最低 25% の明るさ) に従う (ただし遠くても消さない)。
- ホストの固定条件 420 フレームで、変更前と差のある画素は 0.11% (マーカーの塗りと線の描画規則)。

### render 層の三角関数と地平線判定

render 層のエフェクト・マーカー・オーラは float だが、`sinf` / `cosf` は使わない (FPU の無いコアではライブラリ呼び出しで
1 回数千サイクル)。src/render/trig.hpp の `fastSin()` / `fastCos()` が sim の sin 表
(1025 点、線形補間、誤差 ~1e-6) を float に変換して返す。renderer.cpp、effects.cpp、upgrades.cpp が使う。浮遊フラグメント・弾・エンティティの「地平線の向こう側か」の判定は、
float に変換する前に Q30 の内積 (`camQ_.unit`、`camQ_.cosHorizon`) で行い、
向こう側のものには float の計算を一切しない。

### ワイヤーフレームの分割判定

面をどこまで分割するか (`wantLevel()`) は「面の最寄り点がプレイヤーから R FU 以内か」で決める。
これは `ang - faceAngle < R / SPHERE_R`、つまり `cos(ang) > cos(faceAngle + R / SPHERE_R)` と
同じで、右辺はレベルとシフトだけで決まるので走査ごとに表 (`cosLevel5_` / `cosLevel6_`) に
しておき、面ごとの判定は内積 1 回にしている。以前は面ごとに `acos` を呼んでいて、
FPU の無い RP2040 ではそれだけで走査の残り全部より重かった。
プレイヤー方向の単位ベクトルも走査ごとに 1 回 (`playerUnit_`)。
飛行中に領域の半径が 0 まで縮んだら閾値を `INT32_MAX` にして、判定を常に偽にする。
丸めの違いで閾値ぎりぎりの面の段数が変わることがあり、固定条件 21 本中 2 本で
フレームハッシュが変わったが、見た目は同じ。

### フェーズ計測

`devoursphere::profileClockUs` (include/devoursphere/profile.hpp) にマイクロ秒の時計を入れると、
`Game::tick()` と `Renderer::beginFrame()` がフェーズごとの所要時間を積算する
(`Game::tickProfile()` / `Renderer::frameProfile()`、それぞれ `TickPhase` / `FramePhase` のスロット。
`beginFrame()` はカメラ、エフェクト更新、星とワイヤーフレーム、エンティティ、浮遊フラグメント、弾、
エフェクト描画、画面上のオーバーレイ、深度ソートの 9 スロット。
`renderBand()` も 3D と 2D の 2 スロットに積算する)。
時計が無いときのコストはフェーズごとの null 判定 1 回なので常にコンパイルされる。
値は sim が決して読まないので決定性には関係ない。PicoSystem 版と ESPboy 版がオーバーレイに出し、
ベンチマーク (「ベンチマーク」) は実行中だけ全機種で時計を入れて結果に出す。

### ベンチマーク

`render::Benchmark` (include/devoursphere/render/benchmark.hpp) は、決まった場面を毎回同じ手順で
描いて計測し、結果を文字の画面で出す組み込みのベンチマーク。**SPEC に載せる実機の数値はこれで取る**
(同じ場面・同じフレーム列なので、ビルドやライブラリの新旧を比べられる。遊びながら読んだ値は
場面が揃わないので比べられない)。

- **起動**: タイトル画面で B を 3 秒 (`Game::BENCH_HOLD_SECONDS`、tick で数える) 押し続けると、
  `Game` が要求を立てる (`takeBenchmarkRequest()`)。タイトル以外では数えない。全機種で B (緊急回避の
  ボタン) が同じ役割になる。M5StickS3 の KEY2 のように、タイトルで B を別の用途に使っていた機種は
  短押しと長押しで分ける (impl/m5sticks3/SPEC.md)。
- **場面**: 3 つを順に。どれも 1 秒の助走 (計測しない。カメラが落ち着く) と 10 秒の計測。
  1 フレームに必ず 1 tick、dt も 1 tick 分で進め、実時間で待たない (機械が描ける速さで回し、
  その周期を測る)。自機は AI が操縦する。

  | 場面 | スフィア | 武器 | シード | 内容 |
  |---|---|---|---|---|
  | QUIET | 1 | 1 | 1234 | 敵の少ない序盤 |
  | CROWD | 8 | 2 | 7 | 敵が多く画面に入る後半 |
  | FLIGHT | 2 | 2 | 99 | 助走の後に `Game::debugLaunch()` で飛び立ち、LAUNCH 5 秒 + ARRIVE 5 秒 |

  場面は 8 スフィア × 8 シードを 3 種類のビルド (TICK_RATE 60、TICK_RATE 30、ESPboy の縮小構成。
  sim の中身が変わるので混み具合も変わる) で走らせて選んだ。QUIET はどのビルドでも三角形数が
  中央値の 0.7〜0.9 倍、CROWD は 1.3〜2.0 倍で、どの場面でも自機は死なない。
- **再現性**: 場面ごとに `Game::reset(seed)` + `debugStartSphere()` + `Renderer::restart()`
  (カメラの補間、エフェクトとその乱数、スコアの繰り上がり、網の細かさの追従を初期化する。`init()` も
  これを呼ぶ)。ホストで 2 回続けて走らせると全フレームが一致する (`testBenchmark`、TICK_RATE 60 と 30)。
- **ベンチマーク中の `Game`**: `setBenchmark(true)` の間は `scoreIsPlayers()` が偽 (ハイスコアにならない)、
  `sounds()` が 0 (ミュートの設定は変えない)。終わったら新しいシードで `reset()` してタイトルに戻る。
- **計測する値** (場面ごと): フレームの周期 (FPS と平均/最大)、プラットフォームが測った tick の塊・
  `beginFrame`・ラスタライズの平均/最大、表示待ち・コマンド・コア間の待ちの平均 (`BenchSample`)、
  フェーズ計測の平均 (tick は 1 tick あたり、他は 1 フレームあたり)、三角形数とバイト数・スパンの
  ピーク・アリーナ使用量・3D の線の本数の最大、取りこぼしの合計。起動時の全画面転送 (`XFR`) と
  スタックのピークも。
- **結果**: 行が項目、列が 3 つの場面の表 (`Renderer::showTable()`)。一番上に見出し
  (バージョン、機種、画面と TICK_RATE、`XFR`、スタック、ページとキーの案内) を画面の幅に詰めて並べ、
  その下に表を置く。**レンダラが画面に合わせて配置を選ぶ**: フォントを等幅 (6x10 px)、ShapoSansP の 7 px、
  5 px の順に (HUD の倍率から 1 倍まで) 試し、表を画面の幅に入るだけ横に並べ (行を分けて左右に)、
  **ページ数が最少のもののうち一番大きいフォント**にする。1 ページに収まるときは左右の行数を揃える。
  見出しは最初のページだけで、2 ページ目以降は案内の 1 行だけ。行は 1 行おきに地を付ける。
  実測のレイアウト (host で確認): 128x128 は 2 ページ (5 px。ESPboy は `CMD` / `W` / `STK1` の行が無いので
  33 行)、240x135・240x240・320x240・480x320・640x360 は 1 ページ。A で次のページ、B (または最後の
  ページで A) で閉じる。閉じた後は全部のボタンが離されるまでゲームに入力を渡さない。
  シリアルのある機種は同じ表を等幅の文字で `setPlatform()` のログ関数に出す (SPEC にそのまま貼れる形):

  ```
  BENCHMARK v3.4  PICOSYSTEM  240x240 T30  XFR 16.6  STK0 2340  STK1 2592
          QUIET  CROWD FLIGHT
  FPS      30.1   29.8   30.5     FPS
  FRM      33.2   33.5   32.8     フレーム周期の平均 (ms)。以下 ^ は最大
  FRM^     41.0   44.2   38.0
  TCK      16.5   17.3   15.9     tick の塊 (平均 / ^ 最大)
  BGN      13.2   16.4   12.0     beginFrame
  RAS       9.5   11.4    8.8     帯のラスタライズ (計測パネル込み)
  DMA       5.9    4.0    6.1     表示待ち (平均)
  CMD       0.3    0.3    0.3     帯ごとのコマンド (平均)
  W         0.0    1.0    0.0     コア間の待ち (平均)
  TRI        77    150     34     三角形 (最大)
  TRIK        5      9      2     そのバイト数 (KB、最大)
  SPN        22     24     12     スパンのピーク (最大)
  ARNK        9     14      7     アリーナ使用量 (KB、最大)
  LIN        71    190    756     3D パイプラインに入れた線の本数 (最大)
  DRP         0      0      0     取りこぼし (合計。0 でも出す)
  tAI  tMOV tLAY tFIR tBUL tFRG tEAT tETC      tick のフェーズ (1 tick あたり)
  fCAM fSPH fENT fFRG fBUL fEFX fOVL f3D f2D   フレームのフェーズ (1 フレームあたり)
  ```

  (`^` の行は TCK / BGN / RAS にもある。フェーズの行は 1 行に 1 つ。) フェーズとデバッグ表示の文字の対応:
  `tAI tMOV tLAY tFIR` = `A M L F`、`tBUL tFRG tEAT` = `B F K`、`tETC` = `X` (衝突 + 並べ替え + その他)、
  `fSPH fENT` = `S O`、`fFRG fBUL fEFX fOVL` = `F B E M` (その和が `H`)、`fCAM` = `X` (カメラ + エフェクト更新 + ソート)、
  `f3D f2D` = `D U`。値は 100 ms 未満は小数 1 桁、以上は整数。プラットフォームが測らない値 (3 場面とも 0)
  の行は出さない。
- **読み方の注意**:
  - 1 フレームに 1 tick なので、FPS は描画側と sim 側 (`TCK`) の遅い方で決まる。`W` (コア間の待ち) が
    大きい場面は sim 律速で、遊んでいるとき (tick は TICK_RATE の周期で足りればよい) の FPS とは違う
    (PicoSystem の CROWD: `TCK` 22.2 ms、`W` 6.5 ms で 22.3 fps)。シングルコアの ESPboy は遊んでいるときの
    1 フレーム 2 tick に対して 1 tick なので、遊んでいるときより FPS が高く出る。
  - FLIGHT の `TCK^` は着地前のスフィアの差し替え (`switchSphere()`) の 1 tick。
  - 実機の `TRI` と `LIN` はホストの同じ構成の値と一致する (2026-09-24 に全機種で確認)。場面は機種によらず
    同じで、違うのは TICK_RATE と縮小構成と画面の大きさによる分だけ。
  - スタックのピーク (`STK0` / `STK1`) も同じ場面での値なので、版どうしで比べられる。
- **プラットフォームの組み込み** (benchmark.hpp の先頭のとおり): 1 フレームに 1 回、sim のコアが
  止まっていて `Game` を触れる所 (バッチを回収した後、`beginFrame()` の前、自前のフェーズ表示を
  作った後) で `beforeFrame(game, renderer, sample)` を呼び、その間はフェーズ計測の時計を入れ、
  `beginFrame()` の dt を `dt(ran)`、次のバッチの tick 数を `ticks(owed)`、ゲームに渡すボタンを
  `input(buttons)` から取る。`BenchSample` は直前のフレームの値。

### バージョン

core は `VERSION_MAJOR` / `VERSION_MINOR` / `VERSION_STRING` (config.hpp) を持つ。**メジャーバージョンは
ハイスコアの比較が成り立たなくなるゲームシステムの変更 (スコアの式、制限時間、難易度の構造など) で上げ、
それ以外の変更ではマイナーバージョンを上げる。** ハイスコアを保存するプラットフォーム (WASM 版の
localStorage) はメジャーバージョンと到達スフィアをスコアと一緒に記録し、読み出したときにメジャーが
違えば (バージョンの無い古い記録も) 破棄する。

ハンドヘルド (Xiamocon 2 種と PicoSystem) はフラッシュに保存する。バイト列は `high_score_record.hpp`
(ヘッダのみ) が決める 16 バイトのレコードで、リトルエンディアンに magic `"DSHS"`、`VERSION_MAJOR` (u16)、
到達スフィア (u16)、スコア (u32)、その 12 バイトの CRC-32 (zlib と同じ多項式・反転) の順。
`decodeHighScoreRecord()` は magic・CRC・メジャーのどれかが合わなければ「記録なし」を返すので、
未書き込みのフラッシュ (0xFF 埋め)、壊れた記録、旧メジャーの記録はどれも同じ扱いになる
(`testHighScoreRecord`)。いつ書くかはプラットフォーム側
(impl/xiamocon/devoursphere/include/high_score_store.hpp、両ハンドヘルド共通) が決める。
タイトル画面の右下にバージョンを表示する (HUD の節)。1.0 は制限時間とスコアの式を入れた 2026-09-19 の版、
2.0 は制限時間を 4 分にし、最大の敵にもクリティカルヒットが出るようにし、クリア条件を「懸賞首の全滅」にし、
緊急回避のクールダウンを 0.6 秒にした 2026-09-20 の版。3.0 は死亡時に失う大きさを 25% に減らし、
浮遊フラグメントの吸い寄せを自機の大きさに比例させ、死亡後の巻き返し (自機の残骸を残さない、
巻き返し用の敵、強敵だけを見たリスポーン地点) を入れた 2026-09-21 の版。3.1 は初心者向けにスフィア 1 と 2 の
制限時間を 6 分・5 分に延ばし、育った自機のカメラのレンズを長くして引き (「レンズ」)、
大きな自機ではダッシュでカメラを動かさないようにし、スフィアの網をカメラから見た画面上の
大きさだけで決めるようにし、地平線のマーカーをスフィアの中心へ傾けた 2026-09-21〜22 の版 (延長分はボーナスの猶予で相殺するので
ハイスコアの比較はそのまま成り立ち、メジャーは 3 のまま)。3.2 は ESPboy 版のリリースに合わせた 2026-09-22 の版で、
既定のビルドの規則と出力は 3.1 と同じ。小さなターゲット向けのビルド時定数 (「縮小構成のためのビルド時定数」)、
深度なしの世界 (`DEVOURSPHERE_NO_DEPTH`)、HUD の帯ごとのスキップ、最内ループの配置フック
(`DEVOURSPHERE_HOT_ATTR`) が入った。3.3 は画面外の敵のオーラの範囲を視野に比例させ、近い順に描き、大きさをサイズ差・濃さを距離で
決めるようにした 2026-09-23 の版 (「気配のオーラ」)。wasm 版だけを公開し、他のデバイス向けにはそれぞれの次のリリースで適用する。
3.4 はベンチマーク (「ベンチマーク」、タイトル画面で B を 3 秒) を入れ、ShapoGFX を 28d841f にした
2026-09-24 の版。ゲームの規則は 3.3 と同じ。3.5 は ShapoGFX を e0f9662 (gfx2d の API の刷新) にした
2026-09-24 の版。ゲームの規則は 3.4 と同じで、画面の違いは HUD のアップグレードと予備コアのアイコンだけ
(多角形の頂点が画素の中心を指すようになり、斜めの辺が 1 画素ずれる。固定条件 13,560 フレームで
差はこの帯の数十画素だけ、文字と 2 倍のタイトルは一致)。

### Entity の詰め方

`Entity` は 224 バイト (`static_assert`、2.0 で 276 から)。メンバは 4 バイト・2 バイト・1 バイトの順に並べ、
パディングは末尾の 2 バイトだけ。bool (`alive` / `isPlayer` / `dashing` / `braking` / `firing` /
`absorbedBig` / `bounty` / `noScore`) は 1 バイトのビットフィールド (3.0 の `noScore` で 8 ビット埋まった)、`rank` と `evadeFrom` は 1 バイト
(エンティティの添字は 224 未満なので `evadeFrom` の「無し」は `NO_ENTITY` = 255。`aiTarget` は
浮遊フラグメントの添字 (512 個) も入るので 16 ビットのまま)。使われていなかった `seed` は削除した
(乱数を 1 つ消費していたので、同じシードでも 1.x とは展開が変わる)。`Fragment` は 16 バイト:
速度 `vx` / `vy` は `updateLayout()` が `vmax` (= 半径/8 + 距離/16、数千まで) にクランプするので 16 ビットで足り、
念のため `vmax` 自体も 32767 で頭打ちにする。読み書きの命令数はほぼ変わらない (ビットフィールドは
AND 1 回)。

### テスト

`core/test/sim_test.cpp` (ctest) は固定小数点演算の精度、決定性 (同じ入力列で
状態ハッシュが一致)、数千 tick 後の不変条件 (フラグメント数と大きさの範囲、単位ベクトルの長さ、
高度が地表より上)、メニュー遷移、死亡、スフィア遷移、難易度 (スフィア倍率、巨大な敵の弾の頭打ち、
Shield と上限の順序、被弾後の無敵、緊急回避、回避行動がレベル 1 では出ずレベル 4 では離脱と反撃の両方が
出ること)、懸賞首 (最大の敵に付く、自機が最大でも懸賞首が生きていればクリアしない、2 体目、圏外で
下りるが最後の 1 体は下りない、死んで 4 秒でクリア、`sizeof(Entity)`)、制限時間 (レベルごとの長さ、時計が止まる条件、残り 30 秒の警報が 30 回、時間切れの砕け散りと同じスフィアの
やり直し、予備コアが無ければ DEAD)、猶予を使い切ったスフィア 1 の突破ボーナスが基礎点だけになること、
レベル倍率 1.1^(N−1)、ベンチマーク (`testBenchmark`: B 3 秒の起動と、1 tick 足りないと起動しないこと、
実行中はハイスコアにも音にもならないこと、2 回の実行で全フレームが一致すること、結果を閉じた後の入力の
抑止) を検査する。`-DDEVOURSPHERE_SANITIZE=ON` で
ASan/UBSan 付きでビルドできる。
`sim_bench` は AI にプレイヤーを操作させてバランスと tick の処理時間を表示し、最後に `SUMMARY` 行
(生存秒数、死亡数、被ダメージ/秒、自機を狙っている敵の数の体格別内訳、大きさが倍化した時刻) を出す。
`sim_bench ttk` は定数から「同サイズ〜4 倍の敵に撃たれ続けたときの生存秒数」の表を出す。
`core/tools/bench_levels.sh` はレベル 1〜10 × 3 シードの SUMMARY を並べる (AI 自機は弱い代理なので、
曲線の前後比較と単調性の確認に使い、最終判断は実機のプレイテスト)。
